# Improving Discovery of Known Software Vulnerability For Enhanced Cybersecurity

<div class="ltx_authors">

<span class="ltx_creator ltx_role_author"> <span class="ltx_personname">Devesh Sawant </span></span> <span class="ltx_author_before">  </span><span class="ltx_creator ltx_role_author"> <span class="ltx_personname">Manjesh K. Hanawal </span></span> <span class="ltx_author_before">  </span><span class="ltx_creator ltx_role_author"> <span class="ltx_personname">Atul Kabra </span><span class="ltx_author_notes"><span class="ltx_author_notes_content"> <span class="ltx_contact ltx_role_affiliation"><span class="ltx_contact_name">Affiliation: </span>MLiONS Lab, Department of IEOR, IIT Bombay, Mumbai </span></span></span></span>

</div>

<div id="abstract1" class="ltx_abstract">

###### Abstract

Software vulnerabilities are commonly exploited as attack vectors in cyberattacks. Hence, it is crucial to identify vulnerable software configurations early to apply preventive measures. Effective vulnerability detection relies on identifying software vulnerabilities through standardized identifiers such as Common Platform Enumeration (CPE) strings. However, non-standardized CPE strings issued by software vendors create a significant challenge. Inconsistent formats, naming conventions, and versioning practices lead to mismatches when querying databases like the National Vulnerability Database (NVD), hindering accurate vulnerability detection.

Failure to properly identify and prioritize vulnerable software complicates the patching process and causes delays in updating the vulnerable software, thereby giving attackers a window of opportunity. To address this, we present a method to enhance CPE string consistency by implementing a multi-layered sanitization process combined with a fuzzy matching algorithm on data collected using Osquery. Our method includes a union query with priority weighting, which assigns relevance to various attribute combinations, followed by a fuzzy matching process with threshold-based similarity scoring, yielding higher confidence in accurate matches. Comparative analysis with open-source tools such as FleetDM demonstrates that our approach improves detection accuracy by 40%.

<div id="S1" class="section ltx_section">

## <span class="ltx_tag ltx_tag_section">I </span><span id="S1.1" class="ltx_text ltx_font_smallcaps">Introduction</span>

<div id="S1.p1" class="ltx_para">

Software vulnerabilities are a pervasive issue in the modern digital landscape, posing significant security risks to organizations across industries. Vulnerabilities are typically defined as weaknesses or flaws in software code that, if exploited by an attacker, can compromise the confidentiality, integrity, and availability of data. Exploitable vulnerabilities are highly sought after by malicious actors aiming to infiltrate systems, steal sensitive data, disrupt operations, or install malware. High-profile incidents of cyberattacks exploiting known vulnerabilities, such as Heartbleed \[<a href="#bib.bib1" class="ltx_ref">1</a>\] and Log4j \[<a href="#bib.bib2" class="ltx_ref">2</a>\], demonstrate the necessity of a robust vulnerability management process to safeguard systems and reduce the risk of breaches.

</div>

<div id="S1.p2" class="ltx_para">

Vulnerabilities are frequently leveraged in attacks mapped to MITRE ATT&CK \[<a href="#bib.bib3" class="ltx_ref">3</a>\] TTPs. For instance, tactics such as <span id="S1.p2.1.1" class="ltx_text ltx_font_italic">Initial Access (TA0001)</span>, <span id="S1.p2.1.2" class="ltx_text ltx_font_italic">Execution (TA0002)</span>, and <span id="S1.p2.1.3" class="ltx_text ltx_font_italic">Privilege Escalation (TA0004)</span> often exploit unpatched vulnerabilities. Techniques like <span id="S1.p2.1.4" class="ltx_text ltx_font_italic">Exploitation of Remote Services (T1210)</span>, <span id="S1.p2.1.5" class="ltx_text ltx_font_italic">Valid Accounts (T1078)</span>, and <span id="S1.p2.1.6" class="ltx_text ltx_font_italic">Vulnerability Scanning (T1595.002)</span> highlight the critical role of vulnerabilities in the early stages of cyberattacks. By mapping these techniques, organizations can better understand how vulnerabilities serve as key enablers for sophisticated threat actors.

</div>

<div id="S1.p3" class="ltx_para">

Organizations that depend on complex, interconnected software systems are particularly vulnerable, as a single unpatched vulnerability can serve as an entry point for widespread compromise. Consequently, efficient detection of vulnerabilities is crucial for risk management, allowing security teams to address weaknesses before they are exploited. Vulnerability detection tools frequently use standardized identifiers known as <span id="S1.p3.1.1" class="ltx_text ltx_font_italic">Common Platform Enumeration</span> (CPE) \[<a href="#bib.bib4" class="ltx_ref">4</a>\] strings to map software and hardware to known vulnerabilities cataloged in resources such as the <span id="S1.p3.1.2" class="ltx_text ltx_font_italic">National Vulnerability Database</span> (NVD) \[<a href="#bib.bib5" class="ltx_ref">5</a>\]. Each vulnerability in the NVD is associated with a <span id="S1.p3.1.3" class="ltx_text ltx_font_italic">Common Vulnerability and Exposure</span> (CVE) identifier, which links it to affected software configurations through CPE strings.

</div>

<div id="S1.SS1" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S1.SS1.4" class="ltx_text">I-A</span> </span><span id="S1.SS1.5" class="ltx_text ltx_font_italic">Motivation and Problem Statement</span>

<div id="S1.SS1.p1" class="ltx_para">

The motivation behind this study is rooted in the gap between the idea of CPE string standardization and the reality of software vendor’s inconsistent implementations. Many vendors follow proprietary naming and versioning practices, leading to significant variations in datasets used for vulnerability detection. This lack of consistency becomes a barrier to effective vulnerability management, as security teams may miss vulnerabilities when exact CPE string matches are required. Open-source platforms, including FleetDM, rely on exact or near-exact string matching methods. While FleetDM is effective for software monitoring, it lacks advanced mechanisms to accommodate CPE string variations, which can result in missed detections and potential risks for organizations.

</div>

</div>

<div id="S1.SS2" class="section ltx_subsection">

<div id="S1.SS2.p1" class="ltx_para">

In this work, we aim to improve the detection of software vulnerabilities by addressing the challenges posed by non-standardized CPE strings. Our primary contributions include:

- <span id="S1.I1.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S1.I1.i1.p1" class="ltx_para">

  We develop a scalable system architecture that integrates data collection, sanitization, query processing, and fuzzy matching into a seamless pipeline for real-time vulnerability management.

  </div>
- <span id="S1.I1.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S1.I1.i2.p1" class="ltx_para">

  We perform a multi-step sanitization process to standardize software names, versions, and vendor information, thereby addressing common discrepancies that arise in real-world datasets

  </div>
- <span id="S1.I1.i3"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S1.I1.i3.p1" class="ltx_para">

  To retrieve a list of potential matches, we employ a union query that assigns weights based on the parameters matched (e.g., title, vendor, version). These weights prioritize entries and help establish thresholds for subsequent fuzzy matching, enhancing detection accuracy by focusing on highly relevant candidates.

  </div>
- <span id="S1.I1.i4"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S1.I1.i4.p1" class="ltx_para">

  We develop a fuzzy matching algorithm capable of tolerating minor variations in naming conventions and develop a scoring mechanism that indicates confidence in the matching outcomes.

  </div>
- <span id="S1.I1.i5"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S1.I1.i5.p1" class="ltx_para">

  We demonstrate improvement in vulnerability detection rates over standard methods, using FleetDM \[<a href="#bib.bib6" class="ltx_ref">6</a>\] as a benchmark for comparison.

  </div>

Our approach significantly enhances the accuracy of vulnerability detection and provides a proactive tool for organizations to manage software risks.

## <span class="ltx_tag ltx_tag_section">II </span><span id="S2.1" class="ltx_text ltx_font_smallcaps">Related Work</span>

<div id="S2.p1" class="ltx_para">

Accurate discovery software with known vulnerability relies on the precise identification of software components using standardized identifiers, such as CPE strings. Existing solutions, including FleetDM  \[<a href="#bib.bib6" class="ltx_ref">6</a>\], utilize basic string matching and sanitization techniques to link software products with vulnerabilities in databases such as NVD. However, these methods often fall short due to variations in software names, versions, and vendor details that lead to mismatches. In the following, we review approaches used in the open-source project FleetDM, its limitations, and the motivations for our enhanced methodology. The primary reason to focus on FleetDM is that full details are available, and we could reproduce the outcomes for a fair comparison. Though several proprietary solutions are available for software vulnerability detection, such as Tenable Nessus \[<a href="#bib.bib7" class="ltx_ref">7</a>\] and CrowdStrike Falcon Spotlight \[<a href="#bib.bib8" class="ltx_ref">8</a>\], they are proprietary, and full details about their mechanism are not available.

</div>

<div id="S2.SS1" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S2.SS1.4" class="ltx_text">II-A</span> </span><span id="S2.SS1.5" class="ltx_text ltx_font_italic">FleetDM’s Approach to Vulnerability Detection</span>

<div id="S2.SS1.p1" class="ltx_para">

FleetDM \[<a href="#bib.bib6" class="ltx_ref">6</a>\] is an open-source endpoint security platform that provides an elementary solution to software vulnerability detection by matching software installed on client systems against known vulnerabilities in the NVD. FleetDM’s approach focuses on basic sanitization techniques to normalize software names, vendor information, and versions to improve the accuracy of database lookups.

</div>

<div id="S2.SS1.SSS1" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S2.SS1.SSS1.4" class="ltx_text">II-A</span>1 </span>Basic Sanitization in FleetDM

<div id="S2.SS1.SSS1.p1" class="ltx_para">

FleetDM’s method centers on standardizing software names by removing common suffixes, such as ”Inc.” or ”LLC,” and normalizing cases to lowercase. It also simplifies version numbers by trimming trailing zeros, while removing platform-specific tags and unnecessary metadata where possible. For example:

- <span id="S2.I1.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S2.I1.i1.p1" class="ltx_para">

  The software name ”OpenVPN Technologies, Inc.” is reduced to ”openvpn” by removing extraneous terms and standardizing capitalization.

  </div>

</div>

</div>

<div id="S2.SS1.SSS2" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S2.SS1.SSS2.4" class="ltx_text">II-A</span>2 </span>SQL Union-Based Query Matching

<div id="S2.SS1.SSS2.p1" class="ltx_para">

FleetDM employs union-based SQL queries to match software records against NVD data. These queries rely on different combinations of attributes, such as software name, vendor, and version, with priority weighting to increase matching accuracy. For instance:

- <span id="S2.I2.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S2.I2.i1.p1" class="ltx_para">

  Priority is given to queries matching the <span id="S2.I2.i1.p1.1.1" class="ltx_text ltx_font_typewriter">title</span>, <span id="S2.I2.i1.p1.1.2" class="ltx_text ltx_font_typewriter">vendor</span>, and <span id="S2.I2.i1.p1.1.3" class="ltx_text ltx_font_typewriter">version</span> fields.

  </div>
- <span id="S2.I2.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S2.I2.i2.p1" class="ltx_para">

  Lower-weighted queries might match only the software name and version, providing a fallback if the full title or vendor information does not match.

  </div>

</div>

</div>

</div>

<div id="S2.SS2" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S2.SS2.4" class="ltx_text">II-B</span> </span><span id="S2.SS2.5" class="ltx_text ltx_font_italic">Limitations of FleetDM’s Approach</span>

<div id="S2.SS2.p1" class="ltx_para">

While FleetDM’s methodology provides a functional baseline, it encounters limitations when handling non-standardized CPE strings or complex versioning schemes. These limitations hinder its ability to accurately detect vulnerabilities in cases where software vendors use inconsistent or abbreviated naming conventions. The main limitations include:

</div>

<div id="S2.SS2.SSS1" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S2.SS2.SSS1.4" class="ltx_text">II-B</span>1 </span>Insufficient Sanitization and Normalization

<div id="S2.SS2.SSS1.p1" class="ltx_para">

FleetDM’s basic sanitization is effective for handling straightforward discrepancies, such as minor spelling variations or the removal of suffixes. However, it does not fully address the range of inconsistencies encountered in real-world data. For instance:

- <span id="S2.I3.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S2.I3.i1.p1" class="ltx_para">

  Software titles that differ significantly due to rebranding or regional naming may not match. For example, ”Mozilla Thunderbird” and ”Mozilla” might be treated as distinct entries, even though they refer to the same product.

  </div>
- <span id="S2.I3.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S2.I3.i2.p1" class="ltx_para">

  Platform-specific tags or version indicators, such as ”beta” or ”RC1,” may remain after sanitization, resulting in mismatches with standardized database entries.

  </div>

</div>

</div>

<div id="S2.SS2.SSS2" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S2.SS2.SSS2.4" class="ltx_text">II-B</span>2 </span>Lack of Fuzzy Matching

<div id="S2.SS2.SSS2.p1" class="ltx_para">

FleetDM’s approach relies exclusively on exact matches, even when using union queries with flexible attribute combinations. This method fails to account for minor discrepancies in software names, vendor details, or version formats, leading to missed vulnerabilities. In cases where slight variations exist, FleetDM may overlook potential vulnerabilities, as illustrated below:

- <span id="S2.I4.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S2.I4.i1.p1" class="ltx_para">

  Small typographical differences, such as ”Open VPN” versus ”OpenVPN,” may cause records to be overlooked.

  </div>
- <span id="S2.I4.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S2.I4.i2.p1" class="ltx_para">

  Variants like ”Microsoft Corporation” and ”Microsoft Corp.” are treated as separate entities without fuzzy matching, reducing the system’s ability to detect vulnerabilities accurately.

  </div>

</div>

</div>

</div>

<div id="S2.SS3" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S2.SS3.4" class="ltx_text">II-C</span> </span><span id="S2.SS3.5" class="ltx_text ltx_font_italic">Need for an Enhanced Approach</span>

<div id="S2.SS3.p1" class="ltx_para">

Given these limitations, there is a pressing need for a methodology that combines comprehensive sanitization with fuzzy matching techniques to improve detection accuracy. Addressing variations in software titles, vendor names, and versions requires a solution that can adapt to inconsistencies and accurately match software products with corresponding vulnerabilities. Our proposed solution builds upon FleetDM’s foundational structure but introduces a more rigorous sanitization process and fuzzy matching to address data discrepancies.

</div>

<div id="S2.SS3.p2" class="ltx_para">

In the following sections, we present an enhanced methodology that integrates these advanced techniques, resulting in significantly improved detection rates and reduced false negatives.

</div>

</div>

</div>

<div id="S3" class="section ltx_section">

## <span class="ltx_tag ltx_tag_section">III </span><span id="S3.1" class="ltx_text ltx_font_smallcaps">Proposed Methodology</span>

<div id="S3.p1" class="ltx_para">

The proposed methodology addresses the limitations of existing systems by introducing a structured approach that includes data collection, sanitization, prioritized union queries, and fuzzy matching. These steps work unitedly to improve the accuracy of vulnerability detection and ensure a consistent matching process. This section explains each component in detail.

</div>

<div id="S3.SS1" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S3.SS1.4" class="ltx_text">III-A</span> </span><span id="S3.SS1.5" class="ltx_text ltx_font_italic">Data Collection</span>

<div id="S3.SS1.p1" class="ltx_para">

The data collection process begins with the use of <span id="S3.SS1.p1.1.1" class="ltx_text ltx_font_typewriter">osquery</span> \[<a href="#bib.bib9" class="ltx_ref">9</a>\], an open-source tool designed to gather system information from client devices. <span id="S3.SS1.p1.1.2" class="ltx_text ltx_font_typewriter">osquery</span> queries are used to collect data on installed software, including attributes such as software name, version, and vendor, which are then stored in a <span id="S3.SS1.p1.1.3" class="ltx_text ltx_font_typewriter">programs</span> table. This table serves as the primary source of input data for identifying and matching software products against vulnerabilities.

</div>

<div id="S3.SS1.p2" class="ltx_para">

By using <span id="S3.SS1.p2.1.1" class="ltx_text ltx_font_typewriter">osquery</span>, we ensure lightweight and efficient data collection that has minimal impact on system performance, even when deployed across a large number of client systems \[<a href="#bib.bib10" class="ltx_ref">10</a>\].

</div>

</div>

<div id="S3.SS2" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S3.SS2.4" class="ltx_text">III-B</span> </span><span id="S3.SS2.5" class="ltx_text ltx_font_italic">Sanitization Process</span>

<div id="S3.SS2.p1" class="ltx_para">

The sanitization process is essential for normalizing the collected data and addressing inconsistencies in software names, versions, and vendor information, which frequently arise from variations in how vendors label their products. This process consists of the following steps:

</div>

<div id="S3.SS2.p2" class="ltx_para">

- <span id="S3.I1.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S3.I1.i1.p1" class="ltx_para">

  <span id="S3.I1.i1.p1.1.1" class="ltx_text ltx_font_bold">Standardizing Software Names</span>: Extraneous terms such as ”Technologies,” ”Inc.,” and ”LLC” are removed from software names. Additionally, any architecture strings (e.g., ”x86”), language codes, general remarks (e.g., ”7-zip - The best software”), and suffixes like ”.app” are eliminated. Parentheses and their contents are removed, extra spaces are trimmed, and names are lowercased. Special characters and spacing issues are also corrected, resulting in a consistent format. For example, ”OpenVPN Technologies, Inc.” becomes simply ”openvpn.”

  </div>
- <span id="S3.I1.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S3.I1.i2.p1" class="ltx_para">

  <span id="S3.I1.i2.p1.1.1" class="ltx_text ltx_font_bold">Normalizing Vendor Information</span>: Vendors may be recorded under multiple variations, leading to matching errors. The sanitization process normalizes vendor names, transforming differences (e.g., ”Microsoft Corp.” and ”Microsoft Corporation”) into a uniform format, such as ”Microsoft.”

  </div>
- <span id="S3.I1.i3"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S3.I1.i3.p1" class="ltx_para">

  <span id="S3.I1.i3.p1.1.1" class="ltx_text ltx_font_bold">Simplifying Version Numbers</span>: Version numbers can contain unnecessary tags like beta indicators, build numbers, platform identifiers, and other details. The sanitization process trims these to focus on the core version. For instance, ”2.4.11-I602-Win10” is simplified to ”2.4.11,” ensuring a more accurate match with database entries.

  </div>

</div>

<div id="S3.SS2.p3" class="ltx_para">

This comprehensive sanitization process prepares the data for the query stage, significantly reducing discrepancies that could otherwise prevent accurate matching with records in the National Vulnerability Database (NVD).

</div>

</div>

<div id="S3.SS3" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S3.SS3.4" class="ltx_text">III-C</span> </span><span id="S3.SS3.5" class="ltx_text ltx_font_italic">Union Query and Priority Weighting</span>

<div id="S3.SS3.p1" class="ltx_para">

The system employs SQL <span id="S3.SS3.p1.1.1" class="ltx_text ltx_font_typewriter">UNION</span> queries in the CPE (Common Platform Enumeration) database to retrieve potential matches, with each query structured to prioritize specific attributes based on their significance to accurate matching. Each query tier is assigned a weight, with lower weights reflecting higher confidence in the match. This weighted approach ensures that entries most likely to match the software details are prioritized, improving detection accuracy and reducing false positives.

</div>

<div id="S3.SS3.p2" class="ltx_para">

The query structure is organized as follows:

- <span id="S3.I2.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S3.I2.i1.p1" class="ltx_para">

  <span id="S3.I2.i1.p1.1.1" class="ltx_text ltx_font_bold">Weight 1 (High Priority)</span>: This query matches entries based on the combination of title, vendor, and version, generally providing the most accurate results and highest confidence.

  </div>
- <span id="S3.I2.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S3.I2.i2.p1" class="ltx_para">

  <span id="S3.I2.i2.p1.1.1" class="ltx_text ltx_font_bold">Weight 2 (Moderate Priority)</span>: Matches based on product, vendor, and version, accommodating cases where product names may vary slightly or lack uniformity across sources.

  </div>
- <span id="S3.I2.i3"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S3.I2.i3.p1" class="ltx_para">

  <span id="S3.I2.i3.p1.1.1" class="ltx_text ltx_font_bold">Weight 3 (Low Priority)</span>: Considers both title, product, and version fields with relaxed matching criteria, capturing entries that meet most but not all exact fields.

  </div>
- <span id="S3.I2.i4"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S3.I2.i4.p1" class="ltx_para">

  <span id="S3.I2.i4.p1.1.1" class="ltx_text ltx_font_bold">Weight 4 (Fallback Priority)</span>: Matches on title and version only, which serves as a fallback when vendor data is unavailable or vendor inconsistencies prevent a direct match.

  </div>

</div>

<div id="S3.SS3.p3" class="ltx_para">

This weighted query setup enables a comprehensive yet prioritized list of candidate CPEs for each software entry. By ordering results according to confidence, the system effectively filters out less relevant entries and prioritizes highly probable matches, supporting robust and precise vulnerability detection.

</div>

</div>

<div id="S3.SS4" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S3.SS4.4" class="ltx_text">III-D</span> </span><span id="S3.SS4.5" class="ltx_text ltx_font_italic">Fuzzy Matching with RapidFuzz</span>

<div id="S3.SS4.p1" class="ltx_para">

Following the prioritized union query, a fuzzy matching process refines the list by comparing retrieved CPE entries to software names from the programs table. This stage leverages the <span id="S3.SS4.p1.1.1" class="ltx_text ltx_font_typewriter">RapidFuzz</span> \[<a href="#bib.bib11" class="ltx_ref">11</a>\] library’s <span id="S3.SS4.p1.1.2" class="ltx_text ltx_font_typewriter">fuzz::ratio()</span> function to compute similarity scores between the sanitized software name and corresponding fields (title or product) in the CPE database.

</div>

<div id="S3.SS4.p2" class="ltx_para">

The fuzzy matching workflow proceeds as follows:

- <span id="S3.I3.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S3.I3.i1.p1" class="ltx_para">

  <span id="S3.I3.i1.p1.1.1" class="ltx_text ltx_font_bold">Similarity Calculation</span>: For each candidate CPE entry, fuzzy matching calculates a similarity score between the sanitized software name and the retrieved title. When applicable, it also compares the sanitized name to the product field, increasing the robustness of the matching process.

  </div>
- <span id="S3.I3.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S3.I3.i2.p1" class="ltx_para">

  <span id="S3.I3.i2.p1.1.1" class="ltx_text ltx_font_bold">Threshold-Based Filtering</span>: Candidate entries are filtered according to predefined similarity thresholds based on priority weights. For high-confidence matches (weight 1), the threshold is set to 70% or higher to ensure accuracy. Lower weights employ slightly reduced thresholds, accommodating cases with less detailed information.

  </div>
- <span id="S3.I3.i3"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S3.I3.i3.p1" class="ltx_para">

  <span id="S3.I3.i3.p1.1.1" class="ltx_text ltx_font_bold">Selection of Optimal Match</span>: The system records the highest similarity score across all results. The CPE entry that achieves the top similarity score and meets the threshold is selected as the most likely match, ensuring a high degree of accuracy in the final CPE-to-CVE mapping.

  </div>

</div>

<div id="S3.SS4.p3" class="ltx_para">

By combining weighted union queries with fuzzy matching, the system significantly enhances its ability to detect vulnerabilities accurately, even when minor inconsistencies in naming or formatting are present. This integrated approach supports precise and effective vulnerability detection, directly addressing the challenges associated with non-standardized CPE strings and providing a substantial improvement over traditional exact-match methods.

</div>

</div>

<div id="S3.SS5" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S3.SS5.4" class="ltx_text">III-E</span> </span><span id="S3.SS5.5" class="ltx_text ltx_font_italic">CPE to CVE Mapping</span>

<div id="S3.SS5.p1" class="ltx_para">

Once the <span id="S3.SS5.p1.1.1" class="ltx_text ltx_font_typewriter">cpe_string</span> is stored in the <span id="S3.SS5.p1.1.2" class="ltx_text ltx_font_typewriter">programs</span> table, the next step is mapping each <span id="S3.SS5.p1.1.3" class="ltx_text ltx_font_typewriter">cpe_string</span> to the National Vulnerability Database (NVD) to retrieve relevant Common Vulnerabilities and Exposures (CVE) identifiers. This mapping process ensures that each software component is linked to current vulnerability information, facilitating accurate and timely threat detection.

</div>

<div id="S3.SS5.p2" class="ltx_para">

The mapping process includes the following steps:

</div>

<div id="S3.SS5.p3" class="ltx_para">

- <span id="S3.I4.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S3.I4.i1.p1" class="ltx_para">

  <span id="S3.I4.i1.p1.1.1" class="ltx_text ltx_font_bold">Utilizing a Mapping Engine</span>: The mapping engine takes each <span id="S3.I4.i1.p1.1.2" class="ltx_text ltx_font_typewriter">cpe_string</span> and queries the NVD to retrieve any corresponding CVE entries. This automated retrieval ensures that the system maintains up-to-date vulnerability data for each software component.

  </div>
- <span id="S3.I4.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S3.I4.i2.p1" class="ltx_para">

  <span id="S3.I4.i2.p1.1.1" class="ltx_text ltx_font_bold">Storing CVE Identifiers</span>: Once CVE identifiers are retrieved, they are stored in the system’s database and associated with the respective software in the <span id="S3.I4.i2.p1.1.2" class="ltx_text ltx_font_typewriter">programs</span> table. This structured storage allows for quick access to vulnerability details linked to each application.

  </div>
- <span id="S3.I4.i3"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S3.I4.i3.p1" class="ltx_para">

  <span id="S3.I4.i3.p1.1.1" class="ltx_text ltx_font_bold">Dashboard Presentation</span>: The identified vulnerabilities, now mapped to their associated software, are displayed on a user-accessible dashboard. This dashboard provides security teams with a clear view of vulnerabilities, allowing for prioritization and analysis of mitigation steps.

  </div>

</div>

<div id="S3.SS5.p4" class="ltx_para">

This CPE-to-CVE mapping process enhances the system’s detection capabilities, enabling security teams to quickly access actionable vulnerability information for more effective threat response.

</div>

<div id="S3.SS6" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S3.SS6.4" class="ltx_text">III-F</span> </span><span id="S3.SS6.5" class="ltx_text ltx_font_italic">System Architecture</span>

<div id="S3.SS6.p1" class="ltx_para">

The system architecture for linking Common Platform Enumeration (CPE) identifiers with Common Vulnerabilities and Exposures (CVE) records is outlined as follows:

</div>

<div id="S3.SS6.p2" class="ltx_para">

1.  <span id="S3.I5.i1"><span class="ltx_tag ltx_tag_item">1.</span></span>
    <div id="S3.I5.i1.p1" class="ltx_para">

    <span id="S3.I5.i1.p1.1.1" class="ltx_text ltx_font_bold">Data Collection Scripts:</span>

    - <span id="S3.I5.i1.I1.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
      <div id="S3.I5.i1.I1.i1.p1" class="ltx_para">

      We use Osquery \[<a href="#bib.bib9" class="ltx_ref">9</a>\] for efficient installed software data collection from the endpoints.

      </div>
    - <span id="S3.I5.i1.I1.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
      <div id="S3.I5.i1.I1.i2.p1" class="ltx_para">

      <span id="S3.I5.i1.I1.i2.p1.1.1" class="ltx_text ltx_font_bold">NVD Script:</span> Fetches CVE information from the National Vulnerability Database (NVD) and populates the <span id="S3.I5.i1.I1.i2.p1.1.2" class="ltx_text ltx_font_typewriter">nvd_cves</span> table with details like CVE IDs, descriptions, and severity levels.

      </div>
    - <span id="S3.I5.i1.I1.i3"><span class="ltx_tag ltx_tag_item">•</span></span>
      <div id="S3.I5.i1.I1.i3.p1" class="ltx_para">

      <span id="S3.I5.i1.I1.i3.p1.1.1" class="ltx_text ltx_font_bold">CPE Dictionary Script (cpe_dict.sh):</span> Retrieves the CPE dictionary, which standardizes identifiers for software and hardware platforms. This data is stored in the <span id="S3.I5.i1.I1.i3.p1.1.2" class="ltx_text ltx_font_typewriter">cpe</span> table, mapping software programs to CPEs.

      </div>

    </div>
2.  <span id="S3.I5.i2"><span class="ltx_tag ltx_tag_item">2.</span></span>
    <div id="S3.I5.i2.p1" class="ltx_para">

    <span id="S3.I5.i2.p1.1.1" class="ltx_text ltx_font_bold">Database (PostgreSQL):</span>

    - <span id="S3.I5.i2.I1.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
      <div id="S3.I5.i2.I1.i1.p1" class="ltx_para">

      The database contains three primary tables:

      </div>
    - <span id="S3.I5.i2.I1.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
      <div id="S3.I5.i2.I1.i2.p1" class="ltx_para">

      <span id="S3.I5.i2.I1.i2.p1.1.1" class="ltx_text ltx_font_typewriter">nvd_cves</span>: Stores vulnerability data from NVD, detailing CVE information.

      </div>
    - <span id="S3.I5.i2.I1.i3"><span class="ltx_tag ltx_tag_item">•</span></span>
      <div id="S3.I5.i2.I1.i3.p1" class="ltx_para">

      <span id="S3.I5.i2.I1.i3.p1.1.1" class="ltx_text ltx_font_typewriter">cpe</span>: Holds CPE records, linking software identifiers to their respective CPE strings.

      </div>
    - <span id="S3.I5.i2.I1.i4"><span class="ltx_tag ltx_tag_item">•</span></span>
      <div id="S3.I5.i2.I1.i4.p1" class="ltx_para">

      <span id="S3.I5.i2.I1.i4.p1.1.1" class="ltx_text ltx_font_typewriter">programs</span>: Contains data on software installed across monitored systems, including software name, vendor, and version.

      </div>

    </div>
3.  <span id="S3.I5.i3"><span class="ltx_tag ltx_tag_item">3.</span></span>
    <div id="S3.I5.i3.p1" class="ltx_para">

    <span id="S3.I5.i3.p1.1.1" class="ltx_text ltx_font_bold">CPE Matching Service:</span>

    - <span id="S3.I5.i3.I1.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
      <div id="S3.I5.i3.I1.i1.p1" class="ltx_para">

      Processes data in the <span id="S3.I5.i3.I1.i1.p1.1.1" class="ltx_text ltx_font_typewriter">programs</span> table by sanitizing software names, vendors, and versions to standardize the format.

      </div>
    - <span id="S3.I5.i3.I1.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
      <div id="S3.I5.i3.I1.i2.p1" class="ltx_para">

      Utilizes a fuzzy matching algorithm to find potential CPE matches, ensuring accurate mappings despite inconsistencies in software names, vendors, or versions.

      </div>

    </div>
4.  <span id="S3.I5.i4"><span class="ltx_tag ltx_tag_item">4.</span></span>
    <div id="S3.I5.i4.p1" class="ltx_para">

    <span id="S3.I5.i4.p1.1.1" class="ltx_text ltx_font_bold">CPE to CVE Mapping Engine:</span>

    - <span id="S3.I5.i4.I1.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
      <div id="S3.I5.i4.I1.i1.p1" class="ltx_para">

      Maps identified CPEs to known CVEs from the <span id="S3.I5.i4.I1.i1.p1.1.1" class="ltx_text ltx_font_typewriter">nvd_cves</span> table by cross-referencing data, producing a list of vulnerable programs based on the latest NVD information.

      </div>
    - <span id="S3.I5.i4.I1.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
      <div id="S3.I5.i4.I1.i2.p1" class="ltx_para">

      This process indicates which installed software has known vulnerabilities, based on the CPE matching and provides the associated CVE data.

      </div>

    </div>
5.  <span id="S3.I5.i5"><span class="ltx_tag ltx_tag_item">5.</span></span>
    <div id="S3.I5.i5.p1" class="ltx_para">

    <span id="S3.I5.i5.p1.1.1" class="ltx_text ltx_font_bold">Dashboard:</span>

    - <span id="S3.I5.i5.I1.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
      <div id="S3.I5.i5.I1.i1.p1" class="ltx_para">

      Displays the list of vulnerable programs identified in the system, providing security teams with insights into each program’s associated CVEs and severity.

      </div>

    </div>

</div>

<div id="S3.SS6.p3" class="ltx_para">

Overall, this architecture streamlines vulnerability detection by collecting, sanitizing, matching, and mapping software data to vulnerabilities, making critical information readily available for security response.

</div>

## <span class="ltx_tag ltx_tag_section">V </span><span id="S5.1" class="ltx_text ltx_font_smallcaps">Limitations and Future Work</span>

<div id="S5.p1" class="ltx_para">

This section outlines the current limitations of our methodology, particularly in cases that challenge vulnerability detection accuracy. It also proposes future enhancements aimed at improving the system’s performance, adaptability, and coverage.

</div>

<div id="S5.SS1" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S5.SS1.4" class="ltx_text">V-A</span> </span><span id="S5.SS1.5" class="ltx_text ltx_font_italic">Limitations</span>

<div id="S5.SS1.p1" class="ltx_para">

While our approach has improved accuracy in CPE string generation and vulnerability detection, several limitations remain:

</div>

<div id="S5.SS1.SSS0.Px1" class="section ltx_paragraph">

##### 1. Handling of Non-Standard Application Names

<div id="S5.SS1.SSS0.Px1.p1" class="ltx_para">

Despite sanitization and fuzzy matching, some applications with unique or non-standardized names fall below the threshold for accurate CPE generation. For instance, the program “WinRAR 5.20 (32-bit)” by “win.rar GmbH” is listed in the CPE dictionary as “RARLAB WinRAR 5.20” by “rarlab,” with the CPE string:

</div>

<div id="S5.SS1.SSS0.Px1.p2" class="ltx_para">

``` ltx_verbatim
cpe:2.3:a:rarlab:winrar:5.20:*:*:*:*:*:*:*
```

</div>

<div id="S5.SS1.SSS0.Px1.p3" class="ltx_para">

These discrepancies can hinder the matching process. Custom rules for adjusting program names and vendors during sanitization are required to ensure correct CPE generation, particularly for applications with unique identifiers.

</div>

</div>

<div id="S5.SS1.SSS0.Px2" class="section ltx_paragraph">

##### 2. Threshold Sensitivity in Fuzzy Matching

<div id="S5.SS1.SSS0.Px2.p1" class="ltx_para">

Balancing the sensitivity of fuzzy matching thresholds is challenging. High thresholds may miss legitimate software matches (false negatives), while low thresholds can lead to incorrect matches (false positives). Fine-tuning thresholds based on software characteristics could improve the balance between sensitivity and specificity.

</div>

</div>

<div id="S5.SS1.SSS0.Px3" class="section ltx_paragraph">

##### 3. Dependency on Updated CPE Dictionaries

<div id="S5.SS1.SSS0.Px3.p1" class="ltx_para">

The accuracy of our methodology depends on up-to-date CPE dictionaries. If the dictionary is outdated or lacks entries, vulnerability matching is compromised. Frequent updates are essential to maintain effectiveness in vulnerability detection.

</div>

</div>

</div>

<div id="S5.SS2" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S5.SS2.4" class="ltx_text">V-B</span> </span><span id="S5.SS2.5" class="ltx_text ltx_font_italic">Future Work</span>

<div id="S5.SS2.p1" class="ltx_para">

To address these limitations and enhance detection accuracy, efficiency, and scalability, we propose the following improvements:

</div>

<div id="S5.SS2.SSS0.Px1" class="section ltx_paragraph">

##### Real-Time Data Integration

<div id="S5.SS2.SSS0.Px1.p1" class="ltx_para">

Incorporating real-time data ingestion (e.g., via Apache Kafka) could ensure timely updates to the CPE dictionary and vulnerability data, allowing the system to respond more quickly to emerging threats and keep vulnerability information up-to-date.

</div>

</div>

<div id="S5.SS2.SSS0.Px2" class="section ltx_paragraph">

##### Expanded Vulnerability Sources

<div id="S5.SS2.SSS0.Px2.p1" class="ltx_para">

Currently, the system primarily relies on the National Vulnerability Database (NVD). Integrating additional sources, such as RPM and NPM repositories, would extend coverage to vulnerabilities in Linux and JavaScript ecosystems, making the detection framework more comprehensive.

</div>

</div>

<div id="S5.SS2.SSS0.Px3" class="section ltx_paragraph">

##### Automated Rule-Based Pipeline for Custom Applications

<div id="S5.SS2.SSS0.Px3.p1" class="ltx_para">

Developing an automated rule-based pipeline would streamline detection for applications with unique naming conventions. This pipeline would standardize entries (e.g., adjusting “WinRAR” by “win.rar GmbH” to match “RARLAB WinRAR” by “rarlab”) for accurate CPE generation. The system could identify and apply necessary transformations for known mismatches automatically, enhancing detection accuracy without manual intervention.

</div>

</div>

<div id="S5.SS2.SSS0.Px4" class="section ltx_paragraph">

##### Adaptive Fuzzy Matching Thresholds

<div id="S5.SS2.SSS0.Px4.p1" class="ltx_para">

Implementing adaptive thresholds for fuzzy matching could improve detection accuracy by adjusting sensitivity based on software attributes. For widely used software with established naming conventions, stricter thresholds would reduce false positives, while more lenient thresholds could be applied to ambiguous entries, minimizing false negatives.

</div>

</div>

</div>

</div>

<div id="S6" class="section ltx_section">

## <span class="ltx_tag ltx_tag_section">VI </span><span id="S6.1" class="ltx_text ltx_font_smallcaps">Conclusion</span>

<div id="S6.p1" class="ltx_para">

In this paper, we presented an enhanced methodology for software vulnerability detection by addressing the inconsistencies in Common Platform Enumeration (CPE) strings through sanitization and fuzzy matching. Our approach tackles the limitations of traditional open-source tools like FleetDM by normalizing software names, vendor information, and version numbers, thereby aligning non-standardized CPE strings with database entries more effectively.

</div>

<div id="S6.p2" class="ltx_para">

Our solution demonstrated a 40% improvement in detection accuracy over baseline methods, highlighting the importance of multi-step sanitization combined with similarity-based fuzzy matching. The union query approach, prioritized by relevance, enabled precise filtering, while fuzzy matching tolerated minor discrepancies, ensuring higher reliability in detecting vulnerabilities.

</div>

<div id="S6.p3" class="ltx_para">

This work underscores the impact of adaptive matching algorithms in cybersecurity, with future potential for real-time data ingestion, rule-based adjustments for unique software entries, and expansion to broader vulnerability sources. By integrating these advancements, the proposed methodology offers a scalable and robust framework for enhanced vulnerability management, equipping organizations to proactively mitigate security risks in increasingly diverse software environments.
