<div id="abstract1" class="ltx_abstract">

###### Abstract

The dynamic landscape of cybersecurity demands precise and scalable solutions for vulnerability management in heterogeneous systems, where configuration-specific vulnerabilities are often misidentified due to inconsistent data in databases like the National Vulnerability Database (<span id="abstract1.1.1" class="ltx_text ltx_font_italic">NVD</span>). Inaccurate Common Platform Enumeration (<span id="abstract1.1.2" class="ltx_text ltx_font_italic">CPE</span>) data in <span id="abstract1.1.3" class="ltx_text ltx_font_italic">NVD</span> further leads to false positives and incomplete vulnerability retrieval. Informed by our systematic analysis of <span id="abstract1.1.4" class="ltx_text ltx_font_italic">CPE</span> and <span id="abstract1.1.5" class="ltx_text ltx_font_italic">CVEdeails</span> data, revealing more than 50% vendor name inconsistencies, we propose VulCPE, a framework that standardizes data and models configuration dependencies using a unified CPE schema (uCPE), entity recognition, relation extraction, and graph-based modeling. VulCPE achieves superior retrieval precision (0.766) and coverage (0.926) over existing tools. VulCPE ensures precise, context-aware vulnerability management, enhancing cyber resilience.

## <span class="ltx_tag ltx_tag_section">I </span><span id="S1.1" class="ltx_text ltx_font_smallcaps">Introduction</span>

<div id="S1.p1" class="ltx_para">

Vulnerability management is a cornerstone of effective cyber defense, enabling organizations to prioritize and mitigate risks before attackers can exploit them. However, false positives (FPs) in vulnerability management predominantly stem from limitations in Common Platform Enumeration (CPE) \[<a href="#bib.bib25" class="ltx_ref">25</a>\] data utilized during the correlation process. This initial phase in vulnerability management matches deployed software against vulnerability databases maintained by NIST’s National Vulnerability Database (NVD) (<a href="#bib.bib26" class="ltx_ref">26</a>) and software vendors. Vulnerability scanners either extract granular software package data directly from vendor sources or rely on NIST’s CPE descriptions. While CPE aims to standardize software identification across vendors, empirical evidence suggests significant deficiencies in data accuracy and completeness \[<a href="#bib.bib19" class="ltx_ref">19</a>, <a href="#bib.bib3" class="ltx_ref">3</a>, <a href="#bib.bib9" class="ltx_ref">9</a>, <a href="#bib.bib17" class="ltx_ref">17</a>, <a href="#bib.bib29" class="ltx_ref">29</a>\].

</div>

<div id="S1.p2" class="ltx_para">

Various open-source vulnerability management tools, such as <span id="S1.p2.1.1" class="ltx_text ltx_font_italic">OpenCVE</span>, <span id="S1.p2.1.2" class="ltx_text ltx_font_italic">OSV</span>, <span id="S1.p2.1.3" class="ltx_text ltx_font_italic">cve-search</span>, <span id="S1.p2.1.4" class="ltx_text ltx_font_italic">Trivy</span>, <span id="S1.p2.1.5" class="ltx_text ltx_font_italic">CVEdetails</span> and <span id="S1.p2.1.6" class="ltx_text ltx_font_italic">OpenVAS</span>, aim to improve vulnerability detection through database integration and search capabilities. <span id="S1.p2.1.7" class="ltx_text ltx_font_italic">Trivy</span> \[<a href="#bib.bib23" class="ltx_ref">23</a>\] (container scanner) and <span id="S1.p2.1.8" class="ltx_text ltx_font_italic">OpenVAS</span> \[<a href="#bib.bib14" class="ltx_ref">14</a>\] (network scanner) detect vulnerabilities by matching system components against <span id="S1.p2.1.9" class="ltx_text ltx_font_italic">NVD</span> data. To enhance vulnerability data reliability, <span id="S1.p2.1.10" class="ltx_text ltx_font_italic">OSV</span> \[<a href="#bib.bib13" class="ltx_ref">13</a>\], developed by Google, curates open-source vulnerability data using ecosystem-based identifiers (e.g., npm, pip) instead of CPE, improving data accuracy and validation. <span id="S1.p2.1.11" class="ltx_text ltx_font_italic">OpenCVE</span> \[<a href="#bib.bib6" class="ltx_ref">6</a>\] synchronizes CVE data from sources like NVD, MITRE, and RedHat, while cve-search \[<a href="#bib.bib1" class="ltx_ref">1</a>\] imports CVE and CPE data into a local MongoDB database, supporting fast searches and ranking vulnerabilities by CPE names. <span id="S1.p2.1.12" class="ltx_text ltx_font_italic">CVEdetails</span> \[<a href="#bib.bib8" class="ltx_ref">8</a>\] supplements some missing CPE details but restricts API access to paid users, limiting its availability for programmatic queries. Proprietary tools like <span id="S1.p2.1.13" class="ltx_text ltx_font_italic">Tenable</span> and <span id="S1.p2.1.14" class="ltx_text ltx_font_italic">Fortinet</span> lack transparency, making direct comparisons difficult.

</div>

<div id="S1.p3" class="ltx_para">

Despite these efforts, existing tools struggle with CPE inconsistencies, both FPs and false negatives (FNs), and incomplete mappings, which hinder vulnerability retrieval and integration (<a href="#bib.bib31" class="ltx_ref">31</a>). Solutions relying on keyword searches or static CPE-based matching fail to address system configuration dependencies (<a href="#bib.bib32" class="ltx_ref">32</a>). Tools such as <span id="S1.p3.1.1" class="ltx_text ltx_font_italic">cve-search</span> and <span id="S1.p3.1.2" class="ltx_text ltx_font_italic">OpenCVE</span> streamline retrieval but lack capabilities to mitigate FPs or support context-aware matching. Their reliance on manual processes further limits scalability and practicality in large-scale environments (<a href="#bib.bib24" class="ltx_ref">24</a>). Meanwhile, the heterogeneous nature of software, hardware, and operating system (OS) configurations complicates the accurate mapping of vulnerabilities to affected assets (<a href="#bib.bib12" class="ltx_ref">12</a>, <a href="#bib.bib30" class="ltx_ref">30</a>). These structural limitations in CPE data representation frequently manifest as false positives in vulnerability detection systems, reducing the efficacy of automated security assessment protocols.

</div>

<div id="S1.p4" class="ltx_para">

To address these challenges, we propose VulCPE, a framework that addresses these gaps by leveraging advanced techniques such as Named Entity Recognition (NER), Relation Extraction (RE), and graph-based modeling. Specifically, this work explores the following research questions:

</div>

<div id="S1.p5" class="ltx_para">

<span id="S1.p5.1.1" class="ltx_text ltx_font_bold">RQ1:</span> How do data inconsistencies in vulnerability databases affect retrieval accuracy?

</div>

<div id="S1.p6" class="ltx_para">

<span id="S1.p6.1.1" class="ltx_text ltx_font_bold">RQ2:</span> What role do complex system configurations play in determining vulnerability applicability?

</div>

<div id="S1.p7" class="ltx_para">

<span id="S1.p7.1.1" class="ltx_text ltx_font_bold">RQ3:</span> How can advanced techniques reduce false positives in vulnerability management to enhance cyber resilience?

</div>

<figure id="S1.F1" class="ltx_figure">
<img src="2505.13895v1/VulCPE_full.png" id="S1.F1.g1" class="ltx_graphics ltx_centering ltx_img_landscape" style="aspect-ratio:476/155;" width="476" height="155" alt="Refer to caption" />
<figcaption><span class="ltx_tag ltx_tag_figure">Fig. 1: </span>VulCPE Architecture.</figcaption>
</figure>

<div id="S1.p8" class="ltx_para">

We conducted a comprehensive analysis of the <span id="S1.p8.1.1" class="ltx_text ltx_font_italic">NVD/CPE</span> and <span id="S1.p8.1.2" class="ltx_text ltx_font_italic">CVEdetails</span> datasets to uncover prevalent inconsistency patterns. Our results show that 93.55% of <span id="S1.p8.1.3" class="ltx_text ltx_font_italic">NVD</span> entries contain at least one valid <span id="S1.p8.1.4" class="ltx_text ltx_font_italic">CPE</span> string. However, 81.40% of all defined <span id="S1.p8.1.5" class="ltx_text ltx_font_italic">CPE</span> strings remain unused in the <span id="S1.p8.1.6" class="ltx_text ltx_font_italic">NVD</span>, indicating significant underutilization of available configuration identifiers. Additionally, 14.56% of <span id="S1.p8.1.7" class="ltx_text ltx_font_italic">NVD</span> entries rely on configuration-specific <span id="S1.p8.1.8" class="ltx_text ltx_font_italic">CPEs</span>, which require parsing of logical AND/OR groupings. Naming inconsistencies were identified in 50.18% of vendor names used in CPEs within the official <span id="S1.p8.1.9" class="ltx_text ltx_font_italic">NVD</span> database and in 47.07% of vendor names extracted from <span id="S1.p8.1.10" class="ltx_text ltx_font_italic">CVEdetails</span>, highlighting the need for standardization to enhance data usability.

</div>

<div id="S1.p9" class="ltx_para">

Figure <a href="#S1.F1" class="ltx_ref" title="Fig. 1 ‣ I Introduction ‣ VulCPE: Context-Aware Cybersecurity Vulnerability Retrieval and Management"><span class="ltx_text ltx_ref_tag">1</span></a> illustrates the VulCPE framework. VulCPE employs employs NER and RE models to extract structured entities (vendor, product, version) from vulnerability reports and resolve inconsistencies in naming and formatting. Extracted data is standardized into a unified Common Platform Enumeration (uCPE) schema, which provides a hierarchical and logical representation of configurations. Logical relationships (<span id="S1.p9.1.1" class="ltx_text ltx_font_italic">AND/OR</span>) and dependency structures (e.g., application software running on or alongside an OS) are modeled as directed graphs, enabling context-aware matching of vulnerabilities to system configurations. The system constructs two distinct graphs: a hierarchical graph of vulnerable configurations derived from uCPEs and a system configuration graph representing the system under investigation (SUI). Graph traversal techniques are used to match these configurations, ensuring precise vulnerability applicability assessments. Inconsistencies between configurations are detected using subgraph similarity measures, further reducing FPs.

</div>

<div id="S1.p10" class="ltx_para">

Experimental results demonstrate the efficacy of VulCPE in two key areas. First, NER and RE models achieve state-of-the-art performance, with NER attaining a precision of 0.958 and recall of 0.975, and RE achieving a precision of 0.977 and recall of 0.914. Second, VulCPE significantly outperforms existing tools like <span id="S1.p10.1.1" class="ltx_text ltx_font_italic">cve-search</span> and <span id="S1.p10.1.2" class="ltx_text ltx_font_italic">OpenCVE</span> by achieving high retrieval coverage (0.926) and precision (0.766). Our manually labeled 5k ground-truth Common Platform Enumeration (CVE) reports for NER and RE model training and testing is released and available on IEEE DataPort \[<a href="#bib.bib18" class="ltx_ref">18</a>\].

</div>

## <span class="ltx_tag ltx_tag_section">II </span><span id="S2.1" class="ltx_text ltx_font_smallcaps">Background and Related Work</span>

<div id="S2.SS1" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S2.SS1.4" class="ltx_text">II-A</span> </span><span id="S2.SS1.5" class="ltx_text ltx_font_italic">CPE, SCAP and SWID</span>

<div id="S2.SS1.p1" class="ltx_para">

The NIST Interagency Report 8085 outlines guidance for using Software Identification (SWID) tags to create standardized <span id="S2.SS1.p1.1.1" class="ltx_text ltx_font_italic">CPE</span> names \[<a href="#bib.bib33" class="ltx_ref">33</a>\]. SWID tags, compliant with ISO/IEC 19770-2, enable accurate software identification across asset management and cybersecurity applications \[<a href="#bib.bib34" class="ltx_ref">34</a>\].

</div>

<div id="S2.SS1.p2" class="ltx_para">

<span id="S2.SS1.p2.1.1" class="ltx_text ltx_font_italic">CPE</span> functions as a dictionary for vulnerable products within the NIST Security Content Automation Protocol (SCAP) 1.2 standard. Each <span id="S2.SS1.p2.1.2" class="ltx_text ltx_font_italic">CPE</span> entry includes type, vendor, product, and version information. For example, “<span id="S2.SS1.p2.1.3" class="ltx_text ltx_font_italic">cpe:2.3:o:cisco_xe:3.13.2as:::::::\*</span>” indicates an operating system (o) from vendor “<span id="S2.SS1.p2.1.4" class="ltx_text ltx_font_italic">cisco</span>” with product “<span id="S2.SS1.p2.1.5" class="ltx_text ltx_font_italic">ios_xe</span>” version “<span id="S2.SS1.p2.1.6" class="ltx_text ltx_font_italic">3.13.2as</span>”. According to <span id="S2.SS1.p2.1.7" class="ltx_text ltx_font_italic">NVD</span> \[<a href="#bib.bib28" class="ltx_ref">28</a>\], vulnerability configurations are classified as: (1) Basic Configuration with a single node holding one or more <span id="S2.SS1.p2.1.8" class="ltx_text ltx_font_italic">CPE</span> names; (2) Running On/With Configuration containing multiple nodes with both vulnerable and non-vulnerable <span id="S2.SS1.p2.1.9" class="ltx_text ltx_font_italic">CPE</span> names (Fig. <a href="#S2.F2" class="ltx_ref" title="Fig. 2 ‣ II-A CPE, SCAP and SWID ‣ II Background and Related Work ‣ VulCPE: Context-Aware Cybersecurity Vulnerability Retrieval and Management"><span class="ltx_text ltx_ref_tag">2</span></a>); and (3) Advanced Configuration with multiple nodes and complex sets of <span id="S2.SS1.p2.1.10" class="ltx_text ltx_font_italic">CPE</span> names. In this paper, we refer to both Running On/With and Advanced Configurations as Configuration-Specific CPEs.

</div>

<div id="S2.SS2" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S2.SS2.4" class="ltx_text">II-B</span> </span><span id="S2.SS2.5" class="ltx_text ltx_font_italic">Vulnerability Database Data Quality Analysis</span>

<div id="S2.SS2.p1" class="ltx_para">

Public databases like the CVE repository are commonly used in both research and commercial products for vulnerability analysis \[<a href="#bib.bib2" class="ltx_ref">2</a>\]. Yet, numerous recent investigations have highlighted the difficulties encountered with existing vulnerability databases, advocating for the creation of high-quality datasets \[<a href="#bib.bib7" class="ltx_ref">7</a>\] \[<a href="#bib.bib21" class="ltx_ref">21</a>\] \[<a href="#bib.bib4" class="ltx_ref">4</a>\] \[<a href="#bib.bib11" class="ltx_ref">11</a>\]. For example, Dong et al. \[<a href="#bib.bib9" class="ltx_ref">9</a>\] found significant inconsistencies in software version vulnerabilities reported between <span id="S2.SS2.p1.1.1" class="ltx_text ltx_font_italic">CVE</span> and <span id="S2.SS2.p1.1.2" class="ltx_text ltx_font_italic">NVD</span>, with only a fraction of CVE summaries matching <span id="S2.SS2.p1.1.3" class="ltx_text ltx_font_italic">NVD</span> entries accurately. Hong et al. \[<a href="#bib.bib35" class="ltx_ref">35</a>\] addressed the data inconsistencies and incorrectness in software names and versions, and emphasized the importance of identifying original vulnerable software. Li et al. \[<a href="#bib.bib21" class="ltx_ref">21</a>\] further carried out a comprehensive systematic mapping study focusing on the architecture and application of vulnerability databases. This investigation identifies dependencies on <span id="S2.SS2.p1.1.4" class="ltx_text ltx_font_italic">NVD</span> and CVE databases, while also pointing out a significant shortfall in the existing vulnerability databases for their lack of detailed information and metadata, which poses a challenge to detecting vulnerabilities. Hong et al. \[<a href="#bib.bib16" class="ltx_ref">16</a>\] introduced a novel approach for database construction aimed at augmenting the scope of security patches. Their method involves correlating data from the <span id="S2.SS2.p1.1.5" class="ltx_text ltx_font_italic">NVD</span> database with diverse sources such as repositories (e.g., GitHub), issue trackers (e.g., Bugzilla), and Q&A sites (e.g., Stack Overflow).

</div>

<div id="S2.SS2.p2" class="ltx_para">

These findings emphasize the importance of developing methodologies \[<a href="#bib.bib3" class="ltx_ref">3</a>, <a href="#bib.bib19" class="ltx_ref">19</a>, <a href="#bib.bib15" class="ltx_ref">15</a>\] to enhance data consistency and completeness. Recent advancements in natural language processing \[<a href="#bib.bib20" class="ltx_ref">20</a>, <a href="#bib.bib19" class="ltx_ref">19</a>\], machine learning \[<a href="#bib.bib31" class="ltx_ref">31</a>\] and graph-based \[<a href="#bib.bib10" class="ltx_ref">10</a>\] methods showed potential in extracting useful information from unstructured vulnerability reports. However, the quality of the trained data remains uncertain, which increases the challenges of applying these models in practical settings.

</div>

</div>

<div id="S2.SS3" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S2.SS3.4" class="ltx_text">II-C</span> </span><span id="S2.SS3.5" class="ltx_text ltx_font_italic">NER and RE in Security Domains</span>

<div id="S2.SS3.p1" class="ltx_para">

Security vulnerability reports typically contain critical information such as software names, versions, and steps to reproduce the issue. Chaparro et al. \[<a href="#bib.bib5" class="ltx_ref">5</a>\] employed three distinct approaches, namely regular expressions, heuristics, and machine learning, to extract key elements from bug reports, including observed behavior, expected behavior, and steps to reproduce. In the context of vulnerability data, Semfuzz \[<a href="#bib.bib36" class="ltx_ref">36</a>\] utilized regular expressions to extract software version details from CVE entries, while VIEM \[<a href="#bib.bib9" class="ltx_ref">9</a>\] applied NER and RE techniques to extract software names and versions from vulnerability reports in six databases (e.g., <span id="S2.SS3.p1.1.1" class="ltx_text ltx_font_italic">NVD</span>, ExploitDB and SecurityFocus). VERNIER \[<a href="#bib.bib31" class="ltx_ref">31</a>\], also based on NER, was designed to automatically extract software names from unstructured Chinese and English vulnerability reports and to measure inconsistencies in software names across nine mainstream databases (e.g., CVE, <span id="S2.SS3.p1.1.2" class="ltx_text ltx_font_italic">NVD</span> and CNNVD). This method also used a reward-punishment matrix to detect incorrect software names, aiming to improve database accuracy.

</div>

<div id="S2.SS3.p2" class="ltx_para">

Nevertheless, these existing solutions primarily focus on extracting software names and versions independently, without fully addressing the contextual relationships between vendor, product and version. This results in a fragmented understanding of vulnerabilities, which can lead to inaccurate retrieval and misidentification of relevant vulnerabilities in critical systems. Our work addresses this gap by utilizing <span id="S2.SS3.p2.1.1" class="ltx_text ltx_font_italic">CPE</span> standards in combination with advanced NER and RE techniques to construct a unified, contextual representation of vendor, product, and version information. This graph-based uCPE structure not only captures the relationships among these entities but also allows for sophisticated traversal and configuration matching, enabling more accurate and context-aware vulnerability retrieval. In addition, we design a dedicated database schema optimized for storing and retrieving vulnerabilities based on the uCPE structure. This schema is tailored to efficiently support queries that involve complex configurations, ensuring that vulnerabilities can be retrieved accurately with minimized false positives and false negatives.

</div>

</div>

</div>

<div id="S3" class="section ltx_section">

## <span class="ltx_tag ltx_tag_section">III </span><span id="S3.1" class="ltx_text ltx_font_smallcaps">Data Analysis</span>

<div id="S3.p1" class="ltx_para">

This section examines the structure and inconsistencies in <span id="S3.p1.1.1" class="ltx_text ltx_font_italic">NVD</span> and <span id="S3.p1.1.2" class="ltx_text ltx_font_italic">CPE</span> data, highlighting configuration-based <span id="S3.p1.1.3" class="ltx_text ltx_font_italic">CPE</span> patterns and naming inconsistencies in vendors and products.

</div>

<div id="S3.SS1" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S3.SS1.4" class="ltx_text">III-A</span> </span><span id="S3.SS1.5" class="ltx_text ltx_font_italic">Preliminary Data Analysis of NVD/CPE Entries</span>

<div id="S3.SS1.SSS1" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S3.SS1.SSS1.4" class="ltx_text">III-A</span>1 </span>The Usage of CPE in NVD CVE Entries

<div id="S3.SS1.SSS1.p1" class="ltx_para">

We obtained JSON feeds containing 259,233 vulnerability data from 2002 to 31 Aug 2024 (inclusive) from the official <span id="S3.SS1.SSS1.p1.1.1" class="ltx_text ltx_font_italic">NVD</span> website \[<a href="#bib.bib27" class="ltx_ref">27</a>\]. We then filtered these <span id="S3.SS1.SSS1.p1.1.2" class="ltx_text ltx_font_italic">NVD</span> entries based on their last modified date and excluded vulnerabilities marked as “<span id="S3.SS1.SSS1.p1.1.3" class="ltx_text ltx_font_italic">Rejected</span>” by the <span id="S3.SS1.SSS1.p1.1.4" class="ltx_text ltx_font_italic">NVD</span>, which leads to 244,819 vulnerabilities. The <span id="S3.SS1.SSS1.p1.1.5" class="ltx_text ltx_font_italic">CPE</span> v2.3 Dictionary was manually downloaded from <span id="S3.SS1.SSS1.p1.1.6" class="ltx_text ltx_font_italic">CPE</span> \[<a href="#bib.bib25" class="ltx_ref">25</a>\] and we parsed in total 1,327,827 <span id="S3.SS1.SSS1.p1.1.7" class="ltx_text ltx_font_italic">CPE</span> strings for further analysis. We processed all <span id="S3.SS1.SSS1.p1.1.8" class="ltx_text ltx_font_italic">NVD</span> entries to extract <span id="S3.SS1.SSS1.p1.1.9" class="ltx_text ltx_font_italic">CPE</span>-formatted strings and their associated configuration attributes. Of these 244,819 reviewed vulnerabilities, 229,023 (93.55%) contained at least one valid <span id="S3.SS1.SSS1.p1.1.10" class="ltx_text ltx_font_italic">NVD-CPE</span> string. Subsequent analyses focused on this subset. We noticed that some <span id="S3.SS1.SSS1.p1.1.11" class="ltx_text ltx_font_italic">NVD-CPE</span> strings are not recorded in the official <span id="S3.SS1.SSS1.p1.1.12" class="ltx_text ltx_font_italic">CPE</span> dictionary. Meanwhile, 81.40% of the official <span id="S3.SS1.SSS1.p1.1.13" class="ltx_text ltx_font_italic">CPE</span> strings were never referenced in <span id="S3.SS1.SSS1.p1.1.14" class="ltx_text ltx_font_italic">NVD</span>, indicating a significant portion of unused metadata.

</div>

</div>

<div id="S3.SS1.SSS2" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S3.SS1.SSS2.4" class="ltx_text">III-A</span>2 </span>Running On/With CPE Entries

<div id="S3.SS1.SSS2.p1" class="ltx_para">

Our analysis found that 14.56% of <span id="S3.SS1.SSS2.p1.1.1" class="ltx_text ltx_font_italic">NVD</span> entries specify configuration-specific <span id="S3.SS1.SSS2.p1.1.2" class="ltx_text ltx_font_italic">CPEs</span>, exhibiting four key patterns: OS dependencies (e.g., Product A runs on OS B), Enabled Modules (e.g., Product X is vulnerable when Module Y is enabled), Cloud/Virtualization Environments (e.g., vulnerabilities arise when guest virtual machines impact the host system), and Network Configurations (e.g., vulnerabilities caused by specific firewall rules).

<div id="S3.SS2" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S3.SS2.4" class="ltx_text">III-B</span> </span><span id="S3.SS2.5" class="ltx_text ltx_font_italic">Heuristics for Detecting Inconsistencies</span>

<div id="S3.SS2.p1" class="ltx_para">

In vulnerability databases such as <span id="S3.SS2.p1.1.1" class="ltx_text ltx_font_italic">NVD</span> and <span id="S3.SS2.p1.1.2" class="ltx_text ltx_font_italic">CVEdetails</span>, inconsistencies in vendor and product names present significant challenges for accurate vulnerability retrieval and analysis. Given the large scale of vendor and product entries in these databases, manual identification of inconsistencies is impractical. We therefore filed a set of heuristics to detect and group potential name discrepancies for further validation. These heuristics address key patterns of variation observed.

</div>

<div id="S3.SS2.p2" class="ltx_para">

Inconsistencies in <span id="S3.SS2.p2.2.1" class="ltx_text ltx_font_italic">vendor</span> and <span id="S3.SS2.p2.2.2" class="ltx_text ltx_font_italic">product</span> names are quantified as a pairwise divergence metric, where $\text{sim}\hspace{0pt}{(\text{name}_{1},\text{name}_{2})}$ denotes a similarity function, such as Levenshtein or Cosine similarity, calculated using:

|     |                                                                                                                      |     |                                                                        |
|-----|----------------------------------------------------------------------------------------------------------------------|-----|------------------------------------------------------------------------|
|     | ${{\Delta{(\text{name}_{1},\text{name}_{2})}} = {1 - {\text{sim}\hspace{0pt}{(\text{name}_{1},\text{name}_{2})}}}}.$ |     | <span class="ltx_tag ltx_tag_equationgroup ltx_align_right">(1)</span> |

</div>

<div id="S3.SS2.p3" class="ltx_para">

An inconsistency is detected if the discrepancy is larger than a predefined similarity threshold $\tau$.

</div>

<div id="S3.SS2.p4" class="ltx_para">

Define $P{(V)}$ as the product set of vendor $V$, with ${P_{\text{norm}}\hspace{0pt}{(V)}} = {\{{\text{norm}\hspace{0pt}{(p)}}\mid{p \in {P{(V)}}}\}}$. <span id="S3.SS2.p4.2.1" class="ltx_text">norm</span> is short for <span id="S3.SS2.p4.2.2" class="ltx_text">normalize</span>. Shared Product Ratio (SPR) is:

|     |                                                                                                                                                                                                                                                    |     |                                                                        |
|-----|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----|------------------------------------------------------------------------|
|     | ${{\text{Sim}_{\text{prod}}\hspace{0pt}{(V_{1},V_{2})}} = \frac{|{{P_{\text{norm}}\hspace{0pt}{(V_{1})}} \cap {P_{\text{norm}}\hspace{0pt}{(V_{2})}}}|}{|{{P_{\text{norm}}\hspace{0pt}{(V_{1})}} \cup {P_{\text{norm}}\hspace{0pt}{(V_{2})}}}|}}.$ |     | <span class="ltx_tag ltx_tag_equationgroup ltx_align_right">(2)</span> |

</div>

<div id="S3.SS2.p5" class="ltx_para">

Pairwise heuristics require ${\text{Sim}_{\text{prod}}\hspace{0pt}{(V_{1},V_{2})}} \geq \theta_{p}$ (e.g., 0.5).

</div>

<div id="S3.SS2.p6" class="ltx_para">

All the heuristics apply to inconsistency detection in vendor names. Meanwhile, the first heuristic (Format Variations) is also applied to detect inconsistencies in product names. In these cases, the product similarity condition ($\text{Sim}_{\text{prod}} \geq \theta_{p}$) is replaced with vendor similarity ($\text{Sim}_{\text{vendor}}$), defined as:

|     |                                                                                                     |     |                                                                   |
|-----|-----------------------------------------------------------------------------------------------------|-----|-------------------------------------------------------------------|
|     | ${\text{Sim}_{\text{vendor}}\hspace{0pt}{(P_{1},P_{2})}} = \begin{cases}                            
       1 & {{{{\text{if~}\text{vendor}}\hspace{0pt}{(P_{1})}} = {\text{vendor}\hspace{0pt}{(P_{2})}}}.} \\  
       0 & {\text{otherwise}.}                                                                              
       \end{cases}$                                                                                         |     | <span class="ltx_tag ltx_tag_equation ltx_align_right">(3)</span> |

</div>

<div id="S3.SS2.p7" class="ltx_para">

For example, product names like <span id="S3.SS2.p7.1.1" class="ltx_text ltx_font_italic">Windows 10</span> and <span id="S3.SS2.p7.1.2" class="ltx_text ltx_font_italic">windows-10</span> from the same vendor (Microsoft) would be flagged as inconsistent under the Format Variations rule.

</div>

<div id="S3.SS2.p8" class="ltx_para">

\(1\) Format Variations detects character-level differences in capitalization, punctuation, or special characters.

|     |                                                                                                 |     |                                                                   |
|-----|-------------------------------------------------------------------------------------------------|-----|-------------------------------------------------------------------|
|     | ${\Delta_{\text{format}}\hspace{0pt}{(V_{1},V_{2})}} = \begin{cases}                            
       1 & {{{{\text{if~}\text{norm}}\hspace{0pt}{(V_{1})}} = {\text{norm}\hspace{0pt}{(V_{2})}}}.} \\  
       0 & {\text{otherwise}.}                                                                          
       \end{cases}$                                                                                     |     | <span class="ltx_tag ltx_tag_equation ltx_align_right">(4)</span> |

</div>

<div id="S3.SS2.p9" class="ltx_para">

Inconsistency: $\Delta_{\text{format}} = {1 \land \text{Sim}_{\text{prod}}} \geq \theta_{p}$. E.g., “<span id="S3.SS2.p9.1.1" class="ltx_text ltx_font_italic">Microsoft Corp</span>” and “<span id="S3.SS2.p9.1.2" class="ltx_text ltx_font_italic">microsoft-corp</span>”.

</div>

<div id="S3.SS2.p10" class="ltx_para">

\(2\) Spelling Errors detect inconsistencies due to potential spelling or typographical errors in vendor names using edit distances. This is only applied to vendor names that share the same first letter, based on the linguistic observation that typographical errors rarely affect the initial character of a word. Let $d_{L}\hspace{0pt}{(s_{1},s_{2})}$ be the Levenshtein distance. For vendors with ${|{\text{norm}\hspace{0pt}{(V_{1})}}|} \geq m$ and ${|{\text{norm}\hspace{0pt}{(V_{2})}}|} \geq m$, where $m$ is a minimum length threshold (e.g., $m = 5$), define:

|     |                                                                                                                                                                                                                                                          |     |                                                                   |
|-----|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----|-------------------------------------------------------------------|
|     | ${\text{Sim}_{\text{edit}}\hspace{0pt}{(V_{1},V_{2})}} = {1 - \frac{d_{L}\hspace{0pt}{({\text{norm}\hspace{0pt}{(V_{1})}},{\text{norm}\hspace{0pt}{(V_{2})}})}}{\max{({|{\text{norm}\hspace{0pt}{(V_{1})}}|},{|{\text{norm}\hspace{0pt}{(V_{2})}}|})}}}$ |     | <span class="ltx_tag ltx_tag_equation ltx_align_right">(5)</span> |

|     |                                                                                         |     |                                                                   |
|-----|-----------------------------------------------------------------------------------------|-----|-------------------------------------------------------------------|
|     | ${\Delta_{\text{spelling}}\hspace{0pt}{(V_{1},V_{2})}} = \begin{cases}                  
       1 & {{{{\text{if~}\text{Sim}}_{\text{edit}}\hspace{0pt}{(V_{1},V_{2})}} \geq \tau}.} \\  
       0 & {\text{otherwise}.}                                                                  
       \end{cases}$                                                                             |     | <span class="ltx_tag ltx_tag_equation ltx_align_right">(6)</span> |

</div>

<div id="S3.SS2.p11" class="ltx_para">

Inconsistency: $\Delta_{\text{spelling}} = {1 \land \text{Sim}_{\text{prod}}} \geq \theta_{p}$, with $\tau = 0.8$. E.g., “<span id="S3.SS2.p11.1.1" class="ltx_text ltx_font_italic">Microsoft</span>” and “<span id="S3.SS2.p11.1.2" class="ltx_text ltx_font_italic">Microsfot</span>” have $\text{Sim}_{\text{edit}}$ as 0.89.

</div>

<div id="S3.SS2.p12" class="ltx_para">

\(3\) Substring Matches detect prefixes, suffixes, or substrings embedded within longer names, defined as:

|     |                                                                                                                                                                                            |     |                                                                   |
|-----|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----|-------------------------------------------------------------------|
|     | ${\Delta_{\text{string}}\hspace{0pt}{(V_{1},V_{2})}} = \begin{cases}                                                                                                                       
       1 & {{{{\text{if~}\text{norm}}\hspace{0pt}{(V_{1})}} \subset {{\text{norm}\hspace{0pt}{(V_{2})}} \vee {\text{norm}\hspace{0pt}{(V_{2})}}} \subset {\text{norm}\hspace{0pt}{(V_{1})}}}.} \\  
       0 & {\text{otherwise}.}                                                                                                                                                                     
       \end{cases}$                                                                                                                                                                                |     | <span class="ltx_tag ltx_tag_equation ltx_align_right">(7)</span> |

</div>

<div id="S3.SS2.p13" class="ltx_para">

Inconsistency: $\Delta_{\text{string}} = {1 \land \text{Sim}_{\text{prod}}} \geq \theta_{p}$. E.g., “<span id="S3.SS2.p13.1.1" class="ltx_text ltx_font_italic">Apache</span>” vs. “<span id="S3.SS2.p13.1.2" class="ltx_text ltx_font_italic">Apache Software Foundation</span>”.

</div>

<div id="S3.SS2.p14" class="ltx_para">

\(4\) Product Name as Vendor Name flags instances where products are referenced instead of vendors, defined as:

|     |                                                                                                                                                                                             |     |                                                                   |
|-----|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----|-------------------------------------------------------------------|
|     | $\Delta_{\text{prod}}{(V)} = \begin{cases}                                                                                                                                                  
       1 & {{{\text{if~}\hspace{0pt}{\exists V^{\prime}}} \neq V:{{\text{norm}\hspace{0pt}{(V)}} = {{\text{norm}\hspace{0pt}{(P)}} \land P} \in {P_{\text{norm}}\hspace{0pt}{(V^{\prime})}}}}.} \\  
       0 & {\text{otherwise}.}                                                                                                                                                                      
       \end{cases}$                                                                                                                                                                                 |     | <span class="ltx_tag ltx_tag_equation ltx_align_right">(8)</span> |

</div>

<div id="S3.SS2.p15" class="ltx_para">

E.g., “<span id="S3.SS2.p15.1.1" class="ltx_text ltx_font_italic">Windows</span>” instead of “<span id="S3.SS2.p15.1.2" class="ltx_text ltx_font_italic">Microsoft</span>”.

</div>

<div id="S3.SS2.p16" class="ltx_para">

\(5\) Shared Product Names identify cases where multiple vendors are linked to the same product, defined as:

|     |                                                                                                         |     |                                                                   |
|-----|---------------------------------------------------------------------------------------------------------|-----|-------------------------------------------------------------------|
|     | ${\Delta_{\text{shared}}\hspace{0pt}{(V_{1},V_{2})}} = \begin{cases}                                    
       1 & {{{{\text{if~}\text{Sim}}_{\text{prod}}\hspace{0pt}{(V_{1},V_{2})}} \geq \theta_{\text{high}}}.} \\  
       0 & {\text{otherwise}.}                                                                                  
       \end{cases}$                                                                                             |     | <span class="ltx_tag ltx_tag_equation ltx_align_right">(9)</span> |

</div>

<div id="S3.SS2.p17" class="ltx_para">

E.g., “<span id="S3.SS2.p17.1.1" class="ltx_text ltx_font_italic">Sun Microsystems</span>” and “<span id="S3.SS2.p17.1.2" class="ltx_text ltx_font_italic">Oracle</span>” have post-acquisition overlap $\theta$ as 0.8. For Shared Product Names, the SPR is defined as such:

|     |                                                                                                                                                                                                                                                                                      |     |                                                                    |
|-----|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----|--------------------------------------------------------------------|
|     | ${{\text{Sim}_{\text{prod}}\hspace{0pt}{(V_{1},V_{2})}} = \frac{|{{P_{\text{norm}}\hspace{0pt}{(V_{1})}} \cap {P_{\text{norm}}\hspace{0pt}{(V_{2})}}}|}{m\hspace{0pt}i\hspace{0pt}n\hspace{0pt}{({P_{\text{norm}}\hspace{0pt}{(V_{1})}},{P_{\text{norm}}\hspace{0pt}{(V_{2})}})}}}.$ |     | <span class="ltx_tag ltx_tag_equation ltx_align_right">(10)</span> |

</div>

<div id="S3.SS2.p18" class="ltx_para">

This is to account for cases where a smaller company has been acquired by a larger company, where the smaller company has much fewer products.

</div>

<div id="S3.SS2.p19" class="ltx_para">

These heuristics serve as a foundational approach to detecting potential naming discrepancies that are then manually verified. For example, names such as “<span id="S3.SS2.p19.1.1" class="ltx_text ltx_font_italic">heimdal</span>” , “<span id="S3.SS2.p19.1.2" class="ltx_text ltx_font_italic">heimdalsecurity</span>” and “<span id="S3.SS2.p19.1.3" class="ltx_text ltx_font_italic">heimdal_project</span>” can be grouped and reviewed to determine whether they represent the same entity. If confirmed, they are treated as naming inconsistencies and standardized. An additional layer of validation is integrated by analyzing shared product associations and cross-referencing external sources. Manual verification remains essential to distinguish true inconsistencies from cases where minor differences indicate distinct entities, such as separate firmware versions.

</div>

</div>

<div id="S3.SS3.SSS1.p2" class="ltx_para">

Our enhanced pipeline significantly extends the work of \[<a href="#bib.bib3" class="ltx_ref">3</a>\], which identified 1,835 inconsistent vendor names across 871 groups. In contrast, our method uncovered 65,482 inconsistent name instances grouped into 32,420 vendor clusters, as summarized in Table <a href="#S3.T3" class="ltx_ref" title="TABLE III ‣ III-C1 Inconsistencies in Vendor Data ‣ III-C Inconsistency Analysis ‣ III Data Analysis ‣ VulCPE: Context-Aware Cybersecurity Vulnerability Retrieval and Management"><span class="ltx_text ltx_ref_tag">III</span></a>. Format variations were the most common inconsistency, affecting 29,664 unique vendor groups and 59,424 name instances. These were primarily resolved through case folding, special character normalization, and token reordering. Such variations often arise from differing formatting conventions between <span id="S3.SS3.SSS1.p2.1.1" class="ltx_text ltx_font_italic">CPE</span> and <span id="S3.SS3.SSS1.p2.1.2" class="ltx_text ltx_font_italic">CVEdetails</span>, particularly in the use of capitalization, which can impair retrieval accuracy in case-sensitive systems. Excluding case-related issues, 8838 groups (17606 instances) still exhibited format variations due to other formatting differences. Other inconsistency patterns, including spelling errors, acronyms, sub-string matches, and instances where product names are mistakenly labeled as vendors, are analyzed separately in the subset that excludes format variations.

</div>

<div id="S3.SS3.SSS1.p3" class="ltx_para">

We observed FP pairing from acronym and substring matches, which were flagged during manual validation. To mitigate such errors, we integrated a Shared Product Ratio (SPR) threshold (Equation <a href="#S3.E2" class="ltx_ref" title="In III-B Heuristics for Detecting Inconsistencies ‣ III Data Analysis ‣ VulCPE: Context-Aware Cybersecurity Vulnerability Retrieval and Management"><span class="ltx_text ltx_ref_tag">2</span></a>) as a validation heuristic. Vendor name pairs with an SPR $\geq$ 0.5 were flagged as potential matches, and those with an SPR $\geq$ 0.8 exhibited strong semantic coherence, often reflecting genuine aliasing. This filtering mechanism significantly improved precision by reducing the manual validation workload while maintaining high recall. The resulting Shared Product Names category included 1,594 confirmed vendor groups (3,728 name instances).

</div>

<div id="S3.SS3.SSS1.p4" class="ltx_para">

An important meta-level insight is that while format-based inconsistencies dominate quantitatively, the qualitative complexity and verification cost of semantic inconsistencies (spelling, acronyms, substrings) are substantially higher. These patterns are more likely to propagate errors in downstream tasks such as vulnerability resolution, threat attribution, or software inventory reconciliation.

</div>

<div id="S3.SS3.SSS2" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S3.SS3.SSS2.4" class="ltx_text">III-C</span>2 </span>Inconsistencies in Product Data

<div id="S3.SS3.SSS2.p1" class="ltx_para">

In the analysis of product naming inconsistencies, the first step involved addressing the vendor name discrepancies identified in the previous phase. To achieve this, we remapped vendor names to their most consistent forms, prioritizing the name associated with the highest number of <span id="S3.SS3.SSS2.p1.1.1" class="ltx_text ltx_font_italic">CVEs</span>. This approach was grounded in the assumption that the vendor name linked to the greatest number of <span id="S3.SS3.SSS2.p1.1.2" class="ltx_text ltx_font_italic">CVEs</span> is the most widely accepted representation.

</div>

<div id="S3.SS3.SSS2.p2" class="ltx_para">

Product naming inconsistency analysis focused on the format variation heuristic. This heuristic effectively addressed inconsistencies arising from minor character formatting differences, such as underscores versus hyphens, while minimizing the need for manual validation. By prioritizing format variations, our analysis reduced FPs caused by similar product names across unrelated vendors. Among 225,192 unique products, the format variation heuristic identified 138,722 instances consolidated into 68,746 product groups, and hence 700,26 discrepancies primarily due to minor formatting issues. These findings emphasize the importance of standardized naming conventions to ensure consistency. Without such conventions, errors in vendor names propagate to product names, compounding inconsistencies and undermining data integrity.

</div>

</div>

<div id="S3.SS3.SSS3" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S3.SS3.SSS3.4" class="ltx_text">III-C</span>3 </span>Impact of Data Inconsistency on Vulnerability Retrieval

<div id="S3.SS3.SSS3.p1" class="ltx_para">

Approximately 48.67% (33,062) of the 67,925 vendor names exhibit inconsistencies, with 65,482 entries consolidated into 32,420 standardized names. For vendor names from the <span id="S3.SS3.SSS3.p1.1.1" class="ltx_text ltx_font_italic">CPE</span> dataset and <span id="S3.SS3.SSS3.p1.1.2" class="ltx_text ltx_font_italic">CVEdetails</span>, they each contains 16,444 (50.18%) and 16,697 (47.07%) inconsistencies. Moreover, even just within the consistent vendors, 70,026 product names (31.09% of 225,192) are affected by formatting variations.

</div>

<div id="S3.SS3.SSS3.p2" class="ltx_para">

Naming inconsistencies significantly hinder vulnerability retrieval by disrupting mappings between vulnerabilities and affected systems. Misaligned entries lead to incomplete assessments, where vulnerabilities are either overlooked or incorrectly associated. Such discrepancies delay patch identification and deployment, increasing the exposure window and the risk of exploitation. Moreover, the cumulative effect of these inconsistencies across large datasets can compound the risks, leading to widespread security gaps that are harder to detect and manage, as also discussed in works \[<a href="#bib.bib3" class="ltx_ref">3</a>, <a href="#bib.bib17" class="ltx_ref">17</a>, <a href="#bib.bib31" class="ltx_ref">31</a>\].

</div>

<div id="S3.SS3.SSS3.p3" class="ltx_para">

The analysis highlights that resolving inconsistencies requires scalable approaches to standardize naming conventions and enforce consistency across datasets. Automated normalization techniques, cross-database validation, and metadata enrichment can improve data integrity, enabling more effective vulnerability identification, prioritization, and mitigation.

</div>

</div>

</div>

</div>

## <span class="ltx_tag ltx_tag_section">IV </span><span id="S4.1" class="ltx_text ltx_font_smallcaps">Methodology of VulCPE</span>

<div id="S4.p1" class="ltx_para">

This section provides an overview of VulCPE, detailing its architecture and key components designed for configuration-aware vulnerability retrieval and management.

</div>

<div id="S4.SS1" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S4.SS1.4" class="ltx_text">IV-A</span> </span><span id="S4.SS1.5" class="ltx_text ltx_font_italic">Overview of VulCPE</span>

<div id="S4.SS1.p1" class="ltx_para">

The VulCPE architecture, illustrated in Fig. <a href="#S1.F1" class="ltx_ref" title="Fig. 1 ‣ I Introduction ‣ VulCPE: Context-Aware Cybersecurity Vulnerability Retrieval and Management"><span class="ltx_text ltx_ref_tag">1</span></a>, processes vulnerability data to extract, standardize, and map system configurations for precise vulnerability retrieval.

</div>

<div id="S4.SS1.p2" class="ltx_para">

The workflow begins with the <span id="S4.SS1.p2.1.1" class="ltx_text ltx_font_bold">Data Pre-Processor</span>, which normalizes raw inputs from sources like <span id="S4.SS1.p2.1.2" class="ltx_text ltx_font_italic">NVD</span> and <span id="S4.SS1.p2.1.3" class="ltx_text ltx_font_italic">CVEdetails</span>, to ensure standardized data for downstream modules.

</div>

<div id="S4.SS1.p3" class="ltx_para">

The <span id="S4.SS1.p3.1.1" class="ltx_text ltx_font_bold">Named Entity Recognition (NER) Module</span> extracts cybersecurity-specific entities, including product names, versions, and types, from unstructured text. By leveraging domain-specific rules and configurations, the module ensures extracted entities reflect real-world system configurations.

</div>

<div id="S4.SS1.p4" class="ltx_para">

The <span id="S4.SS1.p4.1.1" class="ltx_text ltx_font_bold">Relation Extraction (RE) Module</span> maps relationships between recognized NER entities, such as product-version pairs, to enable precise configuration modeling.

</div>

<div id="S4.SS1.p5" class="ltx_para">

Subsequently, the <span id="S4.SS1.p5.1.1" class="ltx_text ltx_font_bold">Post Processing Module</span> comprises two key steps. First, the <span id="S4.SS1.p5.1.2" class="ltx_text ltx_font_bold">Vendor & Product Separator</span> resolves vendor-product mappings using predefined heuristic rules and string similarity metrics, ensuring consistency with our canonical dictionaries. Next, with the processed vendor and product, the <span id="S4.SS1.p5.1.3" class="ltx_text ltx_font_bold">Version Converter</span> translates complex version descriptors (e.g., “up to”, “before”) into normalized ranges based on datasets such as <span id="S4.SS1.p5.1.4" class="ltx_text ltx_font_italic">NVD</span>. This step ensures consistency of vulnerable product versions across vulnerability sources.

</div>

<div id="S4.SS1.p6" class="ltx_para">

<span id="S4.SS1.p6.1.1" class="ltx_text ltx_font_bold">uCPE Generator</span> consolidates extracted product, version, and type data into hierarchical configurations, enabling interoperability and precise vulnerability-configuration mapping.

</div>

<div id="S4.SS1.p7" class="ltx_para">

The <span id="S4.SS1.p7.1.1" class="ltx_text ltx_font_bold">Vulnerability Database Constructor</span> structures processed data into a graph-based database $G = {(N,E)}$, where nodes ($N$) represent entities (e.g., uCPE configurations) and edges ($E$) capture relationships (e.g., $e_{\text{AND}}$, $e_{\text{OR}}$) among components. This database facilitates efficient querying and supports configuration-aware vulnerability assessments.

</div>

<div id="S4.SS1.p8" class="ltx_para">

<span id="S4.SS1.p8.1.1" class="ltx_text ltx_font_bold">False Positive Filter</span> employs graph-based matching to refine vulnerability-configuration mappings. The system configuration graph ($G_{\text{sys}}$) and vulnerability graph ($G_{\text{vul}}$) are traversed to evaluate matches based on logical dependencies.

</div>

</div>

<div id="S4.SS2" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S4.SS2.4" class="ltx_text">IV-B</span> </span><span id="S4.SS2.5" class="ltx_text ltx_font_italic">Named Entity Recognition</span>

<div id="S4.SS2.p1" class="ltx_para">

NER module extracts structured entities, namely <span id="S4.SS2.p1.2.1" class="ltx_text ltx_font_italic">vendor</span> ($v_{i}$), <span id="S4.SS2.p1.2.2" class="ltx_text ltx_font_italic">product</span> ($p_{i}$), <span id="S4.SS2.p1.2.3" class="ltx_text ltx_font_italic">version</span> ($v\hspace{0pt}e\hspace{0pt}r_{i}$), and <span id="S4.SS2.p1.2.4" class="ltx_text ltx_font_italic">type</span> $t_{i}$ from unstructured vulnerability reports. Let $T$ represent the text of a report. The extraction process is formally defined as:

|     |                                                                                                         |     |                                                                         |
|-----|---------------------------------------------------------------------------------------------------------|-----|-------------------------------------------------------------------------|
|     | $\text{NER}(T) = \{(v{}_{i},p{}_{i},ver{}_{i},t{}_{i}) \mid v{}_{i},p{}_{i},ver{}_{i},t{}_{i} \in T\}.$ |     | <span class="ltx_tag ltx_tag_equationgroup ltx_align_right">(11)</span> |

</div>

<div id="S4.SS2.p2" class="ltx_para">

Our NER model is built on RoBERTa \[<a href="#bib.bib22" class="ltx_ref">22</a>\], chosen for its ability to capture complex contextual relationships. Input text is tokenized into both word-level and sub-word-level units, ensuring compatibility with out-of-vocabulary terms and multi-token entities. Each token is embedded into a dense vector representation, incorporating positional and sub-word-level embeddings. This approach effectively handles complex version formats with alphanumeric characters and punctuation (e.g., “<span id="S4.SS2.p2.1.1" class="ltx_text ltx_font_italic">v1.0.2-alpha</span>”) and multi-token product names (e.g., “<span id="S4.SS2.p2.1.2" class="ltx_text ltx_font_italic">Google Chrome before 8.0.552.237</span>”).

</div>

<div id="S4.SS2.p3" class="ltx_para">

After initial embedding, tokens are further processed through self-attention layers, enabling the model to assign labels to tokens. The primary label set includes <span id="S4.SS2.p3.1.1" class="ltx_text ltx_font_italic">Product Name (PN)</span>, <span id="S4.SS2.p3.1.2" class="ltx_text ltx_font_italic">Modifier (MOD)</span>, <span id="S4.SS2.p3.1.3" class="ltx_text ltx_font_italic">Version (V)</span>, and <span id="S4.SS2.p3.1.4" class="ltx_text ltx_font_italic">Others (O)</span>. For instance, the previous is assigned “<span id="S4.SS2.p3.1.5" class="ltx_text ltx_font_italic">Google</span>” <span id="S4.SS2.p3.1.6" class="ltx_text ltx_font_italic">(B-PN)</span>, “<span id="S4.SS2.p3.1.7" class="ltx_text ltx_font_italic">Chrome</span>” <span id="S4.SS2.p3.1.8" class="ltx_text ltx_font_italic">(I-PN)</span>, “<span id="S4.SS2.p3.1.9" class="ltx_text ltx_font_italic">before</span>” <span id="S4.SS2.p3.1.10" class="ltx_text ltx_font_italic">(B-MOD)</span> and “<span id="S4.SS2.p3.1.11" class="ltx_text ltx_font_italic">8.0.552.237</span>” <span id="S4.SS2.p3.1.12" class="ltx_text ltx_font_italic">(V)</span>.

</div>

<div id="S4.SS2.p4" class="ltx_para">

The model further integrates a domain-specific gazetteer derived from <span id="S4.SS2.p4.1.1" class="ltx_text ltx_font_italic">CVEdetails</span> \[<a href="#bib.bib8" class="ltx_ref">8</a>\], containing vendor names, product names, and version ranges. This gazetteer is incorporated into a post-processing step to validate and adjust predictions using heuristic rules. For example, if the model labels “<span id="S4.SS2.p4.1.2" class="ltx_text ltx_font_italic">Internet</span>” and “<span id="S4.SS2.p4.1.3" class="ltx_text ltx_font_italic">Explorer</span>” as separate entities, the gazetteer merges them into “<span id="S4.SS2.p4.1.4" class="ltx_text ltx_font_italic">Internet Explorer</span>” under a single PN label. This hybrid approach combines RoBERTa’s probabilistic predictions with deterministic rule-based corrections.

</div>

<div id="S4.SS2.p5" class="ltx_para">

The NER module also captures product types (e.g., application, hardware, or OS). Using the same tokenizer and embeddings, extracted labels are concatenated with product type annotations. For instance, the earlier example is updated as “<span id="S4.SS2.p5.1.1" class="ltx_text ltx_font_italic">Google</span>” <span id="S4.SS2.p5.1.2" class="ltx_text ltx_font_italic">(B-PN-APP)</span>, “<span id="S4.SS2.p5.1.3" class="ltx_text ltx_font_italic">Chrome</span>” <span id="S4.SS2.p5.1.4" class="ltx_text ltx_font_italic">(I-PN-APP)</span>, “<span id="S4.SS2.p5.1.5" class="ltx_text ltx_font_italic">before</span>” <span id="S4.SS2.p5.1.6" class="ltx_text ltx_font_italic">(B-MOD)</span> and “<span id="S4.SS2.p5.1.7" class="ltx_text ltx_font_italic">8.0.552.237</span>” <span id="S4.SS2.p5.1.8" class="ltx_text ltx_font_italic">(V)</span>. This categorization ensures differentiations of product roles in system configurations.

</div>

</div>

<div id="S4.SS3" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S4.SS3.4" class="ltx_text">IV-C</span> </span><span id="S4.SS3.5" class="ltx_text ltx_font_italic">Relation Extraction</span>

<div id="S4.SS3.p1" class="ltx_para">

The RE module identifies relationships between entities extracted by the NER module. With $R$ represents the set of valid relationships, the relationship extraction process is formally defined as:

|     |                                                                                                                                                                                 |     |                                                                         |
|-----|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----|-------------------------------------------------------------------------|
|     | ${{\text{RE}\hspace{0pt}{(v_{i},p_{i},{v\hspace{0pt}e\hspace{0pt}r_{i}},t_{i})}} = \text{True}\Leftrightarrow{{(v_{i},p_{i},{v\hspace{0pt}e\hspace{0pt}r_{i}},t_{i})} \in R}}.$ |     | <span class="ltx_tag ltx_tag_equationgroup ltx_align_right">(12)</span> |

</div>

<div id="S4.SS3.p2" class="ltx_para">

The RE model operates in two steps. It first groups modifiers and versions (e.g., “<span id="S4.SS3.p2.1.1" class="ltx_text ltx_font_italic">before 8.0.552.237</span>”) together as <span id="S4.SS3.p2.1.2" class="ltx_text ltx_font_italic">(MOD_V)</span>. Then entities identified by the NER model are grouped into product-modifier-version <span id="S4.SS3.p2.1.3" class="ltx_text ltx_font_italic">(PN-MOD_V)</span> pairs. For each product <span id="S4.SS3.p2.1.4" class="ltx_text ltx_font_italic">(PN)</span>, all associated modifiers and versions <span id="S4.SS3.p2.1.5" class="ltx_text ltx_font_italic">(MOD_V)</span> within the same sentence are paired. For example, the vulnerability report results in the following four candidate pairs: “<span id="S4.SS3.p2.1.6" class="ltx_text ltx_font_italic">Google Chrome</span>” with “<span id="S4.SS3.p2.1.7" class="ltx_text ltx_font_italic">before 8.0.552.237</span>”; “<span id="S4.SS3.p2.1.8" class="ltx_text ltx_font_italic">Google Chrome</span>” with “<span id="S4.SS3.p2.1.9" class="ltx_text ltx_font_italic">before 8.0.552.344</span>”; “<span id="S4.SS3.p2.1.10" class="ltx_text ltx_font_italic">Google Chrome OS</span>” with “<span id="S4.SS3.p2.1.11" class="ltx_text ltx_font_italic">before 8.0.552.237</span>”; and “<span id="S4.SS3.p2.1.12" class="ltx_text ltx_font_italic">Google Chrome OS</span>” with “<span id="S4.SS3.p2.1.13" class="ltx_text ltx_font_italic">before 8.0.552.344</span>”. Each candidate pair is indexed based on its entity labels and converted into tokenized numerical representations, including token IDs, attention masks, and segment IDs. During inference, the RE model predicts the presence of a valid relationship <span id="S4.SS3.p2.1.14" class="ltx_text ltx_font_italic">(PN-MOD_V)</span> using logits generated from RoBERTa’s classification head, with “<span id="S4.SS3.p2.1.15" class="ltx_text ltx_font_italic">Y</span>” indicating a valid relationship and “<span id="S4.SS3.p2.1.16" class="ltx_text ltx_font_italic">N</span>” indicating its absence. If a valid relationship is detected, the model returns the corresponding <span id="S4.SS3.p2.1.17" class="ltx_text ltx_font_italic">(PN-MOD_V)</span> pairs.

</div>

</div>

<div id="S4.SS4" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S4.SS4.4" class="ltx_text">IV-D</span> </span><span id="S4.SS4.5" class="ltx_text ltx_font_italic">Canonical Dictionary Creation</span>

<div id="S4.SS4.p1" class="ltx_para">

To standardize vendor, product, version and type data across heterogeneous sources, we construct a canonical dictionary of vendor-product-version-type pairs using CPE metadata utilized in NVD and a crawled CVEdetails dataset.

</div>

<div id="S4.SS4.p2" class="ltx_para">

To resolve inconsistencies, a standardization function $S{(n^{\ast},\mathcal{D})}$ maps inconsistent names ($n$) to a canonical form ($n^{\prime}$). $D$ is a dictionary of standardized names, using:

|     |                                                                                                                              |     |                                                                         |
|-----|------------------------------------------------------------------------------------------------------------------------------|-----|-------------------------------------------------------------------------|
|     | ${{S{(n^{\ast})}} = {{\arg\max\limits_{\text{n’} \in \mathcal{D}}}\hspace{0pt}\text{d}\hspace{0pt}{(\text{n},\text{n’})}}}.$ |     | <span class="ltx_tag ltx_tag_equationgroup ltx_align_right">(13)</span> |

</div>

<div id="S4.SS4.p3" class="ltx_para">

The similarity between an extracted name (e.g., vendor $v_{i}$ or product $p_{i}$) and a canonical name $n^{\prime} \in \mathcal{D}$ is computed using similarity calculation, Levenshtein distance is used as an example:

|     |                                                                                                                                     |     |                                                                    |
|-----|-------------------------------------------------------------------------------------------------------------------------------------|-----|--------------------------------------------------------------------|
|     | $${{\text{sim}\hspace{0pt}{(n,n^{\prime})}} = {1 - \frac{\text{Lev}\hspace{0pt}{(n,n^{\prime})}}{\max{({|n|},{|n^{\prime}|})}}}}.$$ |     | <span class="ltx_tag ltx_tag_equation ltx_align_right">(14)</span> |

</div>

<div id="S4.SS4.p4" class="ltx_para">

The canonical name is selected if the similarity exceeds a predefined threshold $\tau$:

|     |                                                                                                                                                                                             |     |                                                                    |
|-----|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----|--------------------------------------------------------------------|
|     | $${{n^{\ast} = {{\arg\max\limits_{n^{\prime} \in \mathcal{D}}}\hspace{0pt}\text{sim}\hspace{0pt}{(n,n^{\prime})}}}\quad{{{\text{if~}\text{sim}}\hspace{0pt}{(n,n^{\prime})}} \geq \tau}}.$$ |     | <span class="ltx_tag ltx_tag_equation ltx_align_right">(15)</span> |

</div>

<div id="S4.SS4.p5" class="ltx_para">

NVD CPE strings are parsed into vendor, product, version, and type. Crawled CVEdetails data is flattened into a similar data frame, extracting vendor, product, and version lists. Next, we normalize both vendor and product names through a standardization process, which lowercases text, removes special characters, and standardizes whitespace. Inconsistency detection leverages heuristics from Section <a href="#S3.SS2" class="ltx_ref" title="III-B Heuristics for Detecting Inconsistencies ‣ III Data Analysis ‣ VulCPE: Context-Aware Cybersecurity Vulnerability Retrieval and Management"><span class="ltx_text ltx_ref_tag">III-B</span></a>: Format Variations, Spelling Variations, Acronyms, Substring Matches, Product Name as Vendor Name, and Shared Product Names. These heuristics are applied to both NVD and CVEdetails data, with consistent entries (via inner joins) forming the canonical dictionary and inconsistent ones (via left-anti joins) mapped to canonical names for traceability. Versions are grouped by normalized vendor-product pairs, combining unique versions from both sources.

</div>

<div id="S4.SS4.p6" class="ltx_para">

In doing so, we obtain a canonical dictionary $\mathcal{D}$ and separate mapping tables linking inconsistent names to canonical ones, supporting precise vulnerability retrieval.

</div>

</div>

<div id="S4.SS5" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S4.SS5.4" class="ltx_text">IV-E</span> </span><span id="S4.SS5.5" class="ltx_text ltx_font_italic">Post Processing</span>

<div id="S4.SS5.p1" class="ltx_para">

The post-processing module processes two input sets or one of them: a set of extracted RE entries $\mathcal{R} = {\{\text{RE}_{\text{entry}_{i}}\mid{i \in I}\}}$, where each $\text{RE}_{\text{entry}_{i}} = {(v_{i},p_{i},\text{ver}_{i},t_{i})}$; and a set of CPE match entries $\mathcal{C} = {\{\text{CPE}_{\text{entry}_{j}}\mid{j \in J}\}}$, where each $\text{CPE}_{\text{entry}_{j}} = {(v_{j},p_{j},\text{ver}_{j},t_{j})}$. We employ $S{(n^{\ast},\mathcal{D})}$ to standardize each $\text{RE}_{\text{entry}_{i}}$ and $\text{CPE}_{\text{entry}_{j}}$ to their canonical forms, as defined in Eq. (<a href="#S4.E13" class="ltx_ref" title="In IV-D Canonical Dictionary Creation ‣ IV Methodology of VulCPE ‣ VulCPE: Context-Aware Cybersecurity Vulnerability Retrieval and Management"><span class="ltx_text ltx_ref_tag">13</span></a>). For vendor standardization, $v_{i}$ is compared against $V_{\text{canonical}} \subset \mathcal{D}$, our canonical dataset of vendor names. After identifying $v^{\ast}$, the residual string is matched against products associated with $v^{\ast}$ in $D$. Product names are similarly standardized.

</div>

<div id="S4.SS5.p2" class="ltx_para">

Version standardization converts textual version descriptions into mathematical constraints or discrete lists. Descriptions such as “<span id="S4.SS5.p2.1.1" class="ltx_text ltx_font_italic">version 1.4 and earlier</span>” becomes “$\leq$<span id="S4.SS5.p2.1.2" class="ltx_text ltx_font_italic"> 1.4</span>”, while “<span id="S4.SS5.p2.1.3" class="ltx_text ltx_font_italic">not affected before version 5.0</span>” becomes “$>$<span id="S4.SS5.p2.1.4" class="ltx_text ltx_font_italic"> 5.0</span>”. CPE-specific constraints, such as “<span id="S4.SS5.p2.1.5" class="ltx_text ltx_font_italic">versionStartIncluding</span>”($\geq$) or “<span id="S4.SS5.p2.1.6" class="ltx_text ltx_font_italic">versionEndExcluding</span>”($<$), are also parsed. Let $v_{\text{desc}}$ be a version description (from $\text{ver}_{i}$ or $\text{ver}_{j}$) and $V_{\text{releases}}$ the set of available versions for a standardized vendor-product pair $(v^{\ast},p^{\ast})$. The version converter maps $v_{\text{desc}}$ to a discrete list:

|     |                                                                                                                                   |     |                                                                    |
|-----|-----------------------------------------------------------------------------------------------------------------------------------|-----|--------------------------------------------------------------------|
|     | $${{\text{List}\hspace{0pt}{(v_{\text{desc}})}} = {\{{v_{k} \in V_{\text{releases}}}\mid{\text{cond}\hspace{0pt}{(v_{k})}}\}}},$$ |     | <span class="ltx_tag ltx_tag_equation ltx_align_right">(16)</span> |

</div>

<div id="S4.SS5.p3" class="ltx_para">

Unlike (<a href="#bib.bib9" class="ltx_ref">9</a>), which assumes sequential versions, our approach supports non-sequential vendor releases. For example, “<span id="S4.SS5.p3.1.1" class="ltx_text ltx_font_italic">Google Chrome before 8.0.552.344</span>” is converted to a list of actual releases: \[0.1.38.1, 0.1.38.2, …, 8.0.552.235\].

</div>

<div id="S4.SS5.p4" class="ltx_para">

The hybrid post-process combines entries from $\mathcal{R}$ and $\mathcal{C}$ to produce a set of normalized uCPE entries using canonical dictionary $\mathcal{D}$. If both $\mathcal{R}$ and $\mathcal{C}$ are empty, the process is skipped. When both $\mathcal{R}$ and $\mathcal{C}$ are non-empty, entries are aligned by computing similarity between standardized vendor-product pairs. If the similarity exceeds $\tau$ and versions align, the CPE entry is prioritized. Unaligned entries are processed independently. Results are cached to avoid redundant computations.

</div>

</div>

<div id="S4.SS6" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S4.SS6.4" class="ltx_text">IV-F</span> </span><span id="S4.SS6.5" class="ltx_text ltx_font_italic">Formation of uCPE</span>

<div id="S4.SS6.p1" class="ltx_para">

The uCPE schema addresses the challenges of complex relationships, such as “<span id="S4.SS6.p1.1.1" class="ltx_text ltx_font_italic">Running On/With</span>” dependencies and nested configurations. A uCPE entry ($\text{uCPE}_{\text{entry}}$) represents the foundational unit of vulnerability configuration, consisting a unique identifier, vendor name, product name, version, and product type (e.g., Application, OS, Hardware).

</div>

<div id="S4.SS6.p2" class="ltx_para">

Configurations are modeled as subgraphs $G_{\text{config}}$, where $N_{\text{uCPE}}$ represents nodes corresponding to individual components, and $E_{\text{config}}$ defines the logical dependencies between components, using:

|     |                                                                |     |                                                                         |
|-----|----------------------------------------------------------------|-----|-------------------------------------------------------------------------|
|     | ${G_{\text{config}} = {(N_{\text{uCPE}},E_{\text{config}})}}.$ |     | <span class="ltx_tag ltx_tag_equationgroup ltx_align_right">(17)</span> |

</div>

<div id="S4.SS6.p3" class="ltx_para">

Each edge in $E_{\text{config}}$ represents either:

- <span id="S4.I1.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S4.I1.i1.p1" class="ltx_para">

  <span id="S4.I1.i1.p1.2.1" class="ltx_text ltx_font_italic">AND</span> relationships where components must coexist:

  |     |                                                                                                          |     |                                                                         |
  |-----|----------------------------------------------------------------------------------------------------------|-----|-------------------------------------------------------------------------|
  |     | ${{({\text{uCPE}_{\text{entry}_{i}} \land \text{uCPE}_{\text{entry}_{j}}})}\rightarrow e_{\text{AND}}}.$ |     | <span class="ltx_tag ltx_tag_equationgroup ltx_align_right">(18)</span> |

  </div>
- <span id="S4.I1.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S4.I1.i2.p1" class="ltx_para">

  <span id="S4.I1.i2.p1.2.1" class="ltx_text ltx_font_italic">OR</span> relationships where at least one component suffices:

  |     |                                                                                                        |     |                                                                         |
  |-----|--------------------------------------------------------------------------------------------------------|-----|-------------------------------------------------------------------------|
  |     | ${{({\text{uCPE}_{\text{entry}_{k}} \vee \text{uCPE}_{\text{entry}_{l}}})}\rightarrow e_{\text{OR}}}.$ |     | <span class="ltx_tag ltx_tag_equationgroup ltx_align_right">(19)</span> |

  </div>

</div>

<div id="S4.SS6.p4" class="ltx_para">

Systems and vulnerabilities are modeled as graphs to represent their configurations and relationships. $N_{\text{sys}}$ and $N_{\text{vul}}$ are nodes representing $\text{uCPE}_{\text{entry}}$ and their associated configurations. $E_{\text{sys}}$ and $E_{\text{vul}}$ are edges capturing logical relationships between <span id="S4.SS6.p4.2.1" class="ltx_text ltx_markedasmath">uCPE</span> entries or configurations, defined as:

|     |                                                                                                                                                    |     |                                                                         |
|-----|----------------------------------------------------------------------------------------------------------------------------------------------------|-----|-------------------------------------------------------------------------|
|     | $G{}_{\text{sys}} = (N{}_{\text{sys}},E{}_{\text{sys}}),G{}_{\text{vul}} = (N{}_{v\hspace{0pt}u\hspace{0pt}l},E{}_{v\hspace{0pt}u\hspace{0pt}l}).$ |     | <span class="ltx_tag ltx_tag_equationgroup ltx_align_right">(20)</span> |

</div>

<div id="S4.SS6.p5" class="ltx_para">

Nodes in $N_{s\hspace{0pt}y\hspace{0pt}s}$ and $N_{v\hspace{0pt}u\hspace{0pt}l}$ represent either individual $\text{uCPE}_{\text{entry}}$ elements or logical combinations. For example:

|     |                                                                                                                                            |     |                                                                         |
|-----|--------------------------------------------------------------------------------------------------------------------------------------------|-----|-------------------------------------------------------------------------|
|     | ${N_{\text{sys}} = {\{\text{uCPE}_{\text{entry}_{i}},{({\text{uCPE}_{\text{entry}_{j}} \vee \text{uCPE}_{\text{entry}_{k}}})},\ldots\}}}.$ |     | <span class="ltx_tag ltx_tag_equationgroup ltx_align_right">(21)</span> |

</div>

<div id="S4.SS6.p6" class="ltx_para">

For hierarchical relationships, the vulnerability graph $G_{\text{vul}}$ for each <span id="S4.SS6.p6.1.1" class="ltx_text ltx_font_italic">CVE</span> aggregates all uCPE configurations:

|     |                                                                                                                       |     |                                                                    |
|-----|-----------------------------------------------------------------------------------------------------------------------|-----|--------------------------------------------------------------------|
|     | $${G_{\text{vul}} = {\bigcup\limits_{i = 1}^{n}{G_{\text{config}}\hspace{0pt}{(\text{uCPE}_{\text{entry}_{i}})}}}}.$$ |     | <span class="ltx_tag ltx_tag_equation ltx_align_right">(22)</span> |

</div>

</div>

<div id="S4.SS7" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S4.SS7.4" class="ltx_text">IV-G</span> </span><span id="S4.SS7.5" class="ltx_text ltx_font_italic">Database Construction and Retrieval</span>

<div id="S4.SS7.p1" class="ltx_para">

The database organizes our extracted information into three collections: <span id="S4.SS7.p1.1.1" class="ltx_text ltx_font_italic">uCPE</span>, <span id="S4.SS7.p1.1.2" class="ltx_text ltx_font_italic">Configurations</span>, and <span id="S4.SS7.p1.1.3" class="ltx_text ltx_font_italic">Vulnerabilities</span>.

</div>

<div id="S4.SS7.p2" class="ltx_para">

The uCPE Collection stores standardized vendor-product-version entries for interoperable vulnerability mapping, leveraging the canonical dictionary.

</div>

<div id="S4.SS7.p3" class="ltx_para">

The Configurations Collection represents sub-graphs ($G_{\text{config}}$, Eq. (<a href="#S4.E17" class="ltx_ref" title="In IV-F Formation of uCPE ‣ IV Methodology of VulCPE ‣ VulCPE: Context-Aware Cybersecurity Vulnerability Retrieval and Management"><span class="ltx_text ltx_ref_tag">17</span></a>)), with each entry containing a unique identifier (<span id="S4.SS7.p3.1.1" class="ltx_text ltx_font_italic">config_id</span>), logical relationship type ($e_{\text{AND}},e_{\text{OR}}$), and references to uCPE nodes, modeling hierarchical dependencies in the vulnerability graph $G_{\text{vul}}$ (Eq. (<a href="#S4.E22" class="ltx_ref" title="In IV-F Formation of uCPE ‣ IV Methodology of VulCPE ‣ VulCPE: Context-Aware Cybersecurity Vulnerability Retrieval and Management"><span class="ltx_text ltx_ref_tag">22</span></a>)).

</div>

<div id="S4.SS7.p4" class="ltx_para">

The Vulnerabilities Collection links vulnerabilities to configurations via $c\hspace{0pt}o\hspace{0pt}n\hspace{0pt}f\hspace{0pt}i\hspace{0pt}g\hspace{0pt}\_\hspace{0pt}i\hspace{0pt}d$, including descriptions, CVSS scores, and exploitability metadata.

</div>

<div id="S4.SS7.p5" class="ltx_para">

Two primary query types are implemented: one retrieves vulnerabilities based on CVE identifiers, while the other fetches vulnerabilities by matching specific product and version details. These queries leverage the hierarchical structure of $G_{s\hspace{0pt}y\hspace{0pt}s}$ and $G_{v\hspace{0pt}u\hspace{0pt}l}$. This structure enhances VulCPE’s precision and supports third-party scanners.

</div>

</div>

<div id="S4.SS8" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S4.SS8.4" class="ltx_text">IV-H</span> </span><span id="S4.SS8.5" class="ltx_text ltx_font_italic">Graph-Based False Positive Filtering</span>

<div id="S4.SS8.p1" class="ltx_para">

Our graph-based FP filtering technique leverages domain-specific cybersecurity knowledge to model relationships between vulnerabilities and assets. This approach incorporates configuration dependencies, logical relationships, and hierarchical asset structures, critical for precise vulnerability applicability assessments.

</div>

<div id="S4.SS8.p2" class="ltx_para">

The applicability of a vulnerability node $n_{v} \in N_{v\hspace{0pt}u\hspace{0pt}l}$ to a system node $n_{s} \in N_{s\hspace{0pt}y\hspace{0pt}s}$ is determined by evaluating their hierarchical configurations.

</div>

<div id="S4.SS8.p3" class="ltx_para">

For simple configurations without logical operators, the matching function evaluates whether the configuration graph of $n_{v}$ is a subgraph of that of $n_{s}$:

|     |                                                                                                                                  |     |                                                                    |
|-----|----------------------------------------------------------------------------------------------------------------------------------|-----|--------------------------------------------------------------------|
|     | $${\text{Match}\hspace{0pt}{(n_{v},n_{s})}} = \begin{cases}                                                                      
       {1,} & {{{\text{if~}\hspace{0pt}G_{\text{config}}\hspace{0pt}{(n_{v})}} \subseteq {G_{\text{config}}\hspace{0pt}{(n_{s})}}},} \\  
       {0,} & \text{otherwise.}                                                                                                          
       \end{cases}$$                                                                                                                     |     | <span class="ltx_tag ltx_tag_equation ltx_align_right">(23)</span> |

</div>

<div id="S4.SS8.p4" class="ltx_para">

For configurations involving logical operators, the matching function evaluates dependencies within $E_{c\hspace{0pt}o\hspace{0pt}n\hspace{0pt}f\hspace{0pt}i\hspace{0pt}g}$. Specifically:

|     |                                                                                                                             |     |                                                                    |
|-----|-----------------------------------------------------------------------------------------------------------------------------|-----|--------------------------------------------------------------------|
|     | $${\text{Match}\hspace{0pt}{(n_{v},n_{s})}} = \begin{cases}                                                                 
       {1,} & {\text{if~}\forall e{}_{\text{AND}} \in E{}_{\text{config}}(n{}_{v}),\text{Match}(e{}_{\text{AND}},n{}_{s}) = 1,} \\  
       {1,} & {\text{if~}\exists e{}_{\text{OR}} \in E{}_{\text{config}}(n{}_{v}),\text{Match}(e{}_{\text{OR}},n{}_{s}) = 1,} \\    
       {0,} & \text{otherwise.}                                                                                                     
       \end{cases}$$                                                                                                                |     | <span class="ltx_tag ltx_tag_equation ltx_align_right">(24)</span> |

</div>

<div id="S4.SS8.p5" class="ltx_para">

This matching process ensures that vulnerabilities are only applied when all <span id="S4.SS8.p5.1.1" class="ltx_text ltx_markedasmath">AND</span> conditions or any <span id="S4.SS8.p5.1.2" class="ltx_text ltx_markedasmath">OR</span> condition in the vulnerable configuration are matched by system configuration.

</div>

<div id="S4.SS8.p6" class="ltx_para">

Further, the filtering process utilizes graph traversal to refine vulnerability applicability. Vulnerabilities ($v$) and SUI are represented as vertices in $G_{\text{vul}}$ and $G_{\text{sys}}$, enriched with logical dependencies. Algorithm <a href="#alg1" class="ltx_ref" title="In IV-H Graph-Based False Positive Filtering ‣ IV Methodology of VulCPE ‣ VulCPE: Context-Aware Cybersecurity Vulnerability Retrieval and Management"><span class="ltx_text ltx_ref_tag">1</span></a> outlines the FP filtering procedure. If a match is found, the vulnerability is added to the set of applicable vulnerabilities ($V_{\text{applicable}}$), as giving by:

|     |                                                                                                                             |     |                                                                         |
|-----|-----------------------------------------------------------------------------------------------------------------------------|-----|-------------------------------------------------------------------------|
|     | ${V_{\text{applicable}} = {V_{\text{vul}} - {\{{v \in V_{\text{vul}}}\mid{{\text{Match}\hspace{0pt}{(v,n_{s})}} = 1}\}}}}.$ |     | <span class="ltx_tag ltx_tag_equationgroup ltx_align_right">(25)</span> |

</div>

<div id="S5" class="section ltx_section">

## <span class="ltx_tag ltx_tag_section">V </span><span id="S5.1" class="ltx_text ltx_font_smallcaps">Implementation</span>

<div id="S5.p1" class="ltx_para">

We leverage several optimization strategies to enable VulCPE to handle large-scale vulnerability data while maintaining accuracy and minimizing computational overhead.

</div>

<div id="S5.SS1" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S5.SS1.4" class="ltx_text">V-A</span> </span><span id="S5.SS1.5" class="ltx_text ltx_font_italic">Parallelization</span>

<div id="S5.SS1.p1" class="ltx_para">

Parallelization is implemented across multiple VulCPE modules to reduce processing time by distributing workloads. In the data pre-processing stage, text normalization and tokenization of vulnerability reports are executed concurrently using multi-threading, allowing independent processing of each report. Similarly, post-processing operations, including string similarity computations for standardizing vendor and product names, are parallelized across CPU cores, while database lookups for version conversions are batched to minimize I/O overhead. In the FP-filtering stage, graph-based subgraph isomorphism checks are distributed across multiple configurations.

</div>

</div>

<div id="S5.SS2" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S5.SS2.4" class="ltx_text">V-B</span> </span><span id="S5.SS2.5" class="ltx_text ltx_font_italic">FP Handling</span>

<div id="S5.SS2.p1" class="ltx_para">

Our method is built upon \[<a href="#bib.bib32" class="ltx_ref">32</a>\] with three key improvements: Firstly, we utilize <span id="S5.SS2.p1.1.1" class="ltx_text ltx_font_italic">uCPE-ID</span> than simply relying on the extracted textual information. Secondly, we use <span id="S5.SS2.p1.1.2" class="ltx_text ltx_font_italic">NetworkX</span> to support graph implementation using <span id="S5.SS2.p1.1.3" class="ltx_text ltx_font_italic">Python</span> to allow easier integration with the whole vulnerability pipeline. Thirdly, we enhance the efficiency of FP filtering by storing the graph locally after its initial creation, and subsequently appending nodes upon the identification of new <span id="S5.SS2.p1.1.4" class="ltx_text ltx_font_italic">CVEs</span> or Assets within the system. This approach significantly optimizes performance in terms of execution time. Empirical evidence from our experiments later in Section <a href="#S6" class="ltx_ref" title="VI Experimental Evaluation ‣ VulCPE: Context-Aware Cybersecurity Vulnerability Retrieval and Management"><span class="ltx_text ltx_ref_tag">VI</span></a> illustrates this improvement: the initial processing of 232 Assets requires approximately 25 minutes and 33 seconds. However, subsequent iterations demonstrate a marked reduction in execution time, involving only the verification of new assets rather than the comprehensive regeneration of the graph. Specifically, the addition of nodes for new assets incurs around 6.6 seconds per node, showcasing the efficiency of our optimized model in dynamically updating with minimal computational overhead.

</div>

</div>

<div id="S5.SS3" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S5.SS3.4" class="ltx_text">V-C</span> </span><span id="S5.SS3.5" class="ltx_text ltx_font_italic">Incremental Updates</span>

<div id="S5.SS3.p1" class="ltx_para">

The graph-based vulnerability database is designed to support incremental updates, ensuring that new data can be integrated without requiring a full reconstruction. When new vulnerabilities or configurations are introduced, only the affected graph nodes and edges are updated, avoiding the computational expense of rebuilding the entire structure. This approach is also applied in the FP-filtering process, where the graph is modified incrementally upon the addition of new assets or vulnerabilities. Instead of reprocessing the entire dataset, filtering operations are restricted to newly introduced or updated nodes.

</div>

</div>

</div>

<div id="S6" class="section ltx_section">

## <span class="ltx_tag ltx_tag_section">VI </span><span id="S6.1" class="ltx_text ltx_font_smallcaps">Experimental Evaluation</span>

<div id="S6.p1" class="ltx_para">

This section presents a comprehensive experimental evaluation, with details on dataset, baseline models, evaluation metrics, and key implementation specifics. We focus on:

</div>

<div id="S6.p2" class="ltx_para">

- <span id="S6.I1.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S6.I1.i1.p1" class="ltx_para">

  RQ1: How effective is VulCPE in entity extraction and relation extraction compared to state-of-the-art approaches?

  </div>
- <span id="S6.I1.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S6.I1.i2.p1" class="ltx_para">

  RQ2: Can VulCPE be effectively applied to vulnerability retrieval in real-world settings?

  </div>

</div>

<div id="S6.SS1" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S6.SS1.4" class="ltx_text">VI-A</span> </span><span id="S6.SS1.5" class="ltx_text ltx_font_italic">Experiment I: NER/RE Evaluation</span>

<div id="S6.SS1.SSS1" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S6.SS1.SSS1.4" class="ltx_text">VI-A</span>1 </span>Dataset

<div id="S6.SS1.SSS1.p1" class="ltx_para">

Previous NER datasets for vulnerability contexts \[<a href="#bib.bib9" class="ltx_ref">9</a>\] utilize simplistic annotation schemes (SN, SV, O) that inadequately capture nuanced entity boundaries and multi-token entities common in vulnerability data. Our review identified significant labeling gaps, necessitating a more comprehensive dataset for structured vulnerability descriptions.

</div>

<div id="S6.SS1.SSS1.p2" class="ltx_para">

We implemented a customized BIO format to label vulnerability reports, generating a ground-truth dataset for NER model training and validation. To enhance model performance, we expanded the NER label schema to include three product categories, replacing all B-PN/I-PN labels with categorized labels to improve <span id="S6.SS1.SSS1.p2.1.1" class="ltx_text ltx_font_italic">uCPE</span> matching and vulnerability retrieval.

</div>

<div id="S6.SS1.SSS1.p3" class="ltx_para">

From our dataset (Section <a href="#S3" class="ltx_ref" title="III Data Analysis ‣ VulCPE: Context-Aware Cybersecurity Vulnerability Retrieval and Management"><span class="ltx_text ltx_ref_tag">III</span></a>), we sampled 5,000 vulnerability descriptions (3,000 pre-2019 and 2,000 post-2019) for balanced temporal representation. Each description was tokenized and initially labeled using GPT-4o, though we observed relatively low accuracy, particularly for modifier (MOD) and version labeling. Consequently, two security researchers conducted manual reviews to ensure labeling accuracy.

</div>

<div id="S6.SS1.SSS1.p4" class="ltx_para">

To incorporate RE, we developed rules capturing relationships between product entities and their associated versions with modifiers. This approach identifies product-to-version relationships where modifiers define version applicability conditions (e.g., “<span id="S6.SS1.SSS1.p4.1.1" class="ltx_text ltx_font_italic">before</span>” a certain version or “<span id="S6.SS1.SSS1.p4.1.2" class="ltx_text ltx_font_italic">fixed in</span>” a particular release). We generated candidate pairs by linking product entities with version-modifier entities within the same context, assigning position indices for pairing. Additional contextual validation determined logical associations between the product and the version-modifier combination, with pairs labeled as valid (Y) or invalid (N).

</div>

</div>

<div id="S6.SS1.SSS2" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S6.SS1.SSS2.4" class="ltx_text">VI-A</span>2 </span>Evaluation Metrics

<div id="S6.SS1.SSS2.p1" class="ltx_para">

Four main metrics are utilized to validate NER and RE models: (1) Accuracy is the fraction of correct predictions out of all predictions, offering a measure of overall correctness; (2) Precision is the ratio of correctly extracted entities and relations to the total identified, which minimizes false positives; (3) Recall is the proportion of correctly extracted entities and relations out of all relevant ones, which ensures true positives are included; (4) F1 Score is a harmonic mean of precision and recall, providing a balanced evaluation of accuracy and error rates.

</div>

</div>

<div id="S6.SS1.SSS3" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S6.SS1.SSS3.4" class="ltx_text">VI-A</span>3 </span>Implementation Details

<div id="S6.SS1.SSS3.p1" class="ltx_para">

Our NER model employs the RoBERTa architecture via Hugging Face transformers, with labeled BIO format text split into training and testing sets (80-20) using a fixed random seed for reproducibility.

</div>

<div id="S6.SS1.SSS3.p2" class="ltx_para">

For RE, we utilize <span id="S6.SS1.SSS3.p2.1.1" class="ltx_text ltx_font_italic">RoBERTaForSequenceClassification</span> to identify entity relationships. Input sentences are preprocessed by tagging entities with custom tokens, then tokenized into IDs, masks, and segments to generate logits. Valid product-version pairs are extracted based on predictions.

</div>

</div>

<div id="S6.SS1.SSS4" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S6.SS1.SSS4.4" class="ltx_text">VI-A</span>4 </span>NER and RE Performance

<div id="S6.SS1.SSS4.p1" class="ltx_para">

We evaluated our NER model, built on RoBERTa, against state-of-the-art baselines, including VERNIER \[<a href="#bib.bib31" class="ltx_ref">31</a>\] and VIEM \[<a href="#bib.bib9" class="ltx_ref">9</a>\]. VIEM results correspond to its best-performing configuration, incorporating transfer learning and gazetteer features, while VERNIER’s performance is reported for English-language vulnerability reports. We also included TinyLlama \[<a href="#bib.bib37" class="ltx_ref">37</a>\] which is a recent lightweight LLM that achieves competitive performance on token-level tasks. The RE evaluation of baseline models compares the set of predicted product-version relationships against the set of ground-truth relationships per sentence, using a greedy best-match approach with relaxed product aliasing and version matching. Table <a href="#S6.T4" class="ltx_ref" title="TABLE IV ‣ VI-A4 NER and RE Performance ‣ VI-A Experiment I: NER/RE Evaluation ‣ VI Experimental Evaluation ‣ VulCPE: Context-Aware Cybersecurity Vulnerability Retrieval and Management"><span class="ltx_text ltx_ref_tag">IV</span></a> shows that our RoBERTa model with gazetteer achieved an accuracy of 98.56%, precision of 95.77%, recall of 97.54%, and an F1 score of 96.53%, demonstrating comparable performance to both baselines and outperforming simpler configurations such as RoBERTa without a gazetteer.

</div>

<div id="S6.SS1.SSS5" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S6.SS1.SSS5.4" class="ltx_text">VI-A</span>5 </span>Error Analysis

<div id="S6.SS1.SSS5.p1" class="ltx_para">

We conducted thorough error analysis in our models and identified three main patterns. Our NER and RE models face challenges with complex product names and version mismatches. For example, in “<span id="S6.SS1.SSS5.p1.1.1" class="ltx_text ltx_font_italic">Microsoft Word 2007 SP3, Office 2010 SP2</span>”, “<span id="S6.SS1.SSS5.p1.1.2" class="ltx_text ltx_font_italic">2007</span>” is mislabeled as part of the product name (I-PN) instead of a version (B-V).

</div>

<div id="S6.SS1.SSS5.p2" class="ltx_para">

Ambiguity in platform vs. product classification is evident when “<span id="S6.SS1.SSS5.p2.1.1" class="ltx_text ltx_font_italic">iOS</span>” in “<span id="S6.SS1.SSS5.p2.1.2" class="ltx_text ltx_font_italic">Newphoria Auction Camera for iOS</span>” is misclassified as a product (B-PN) instead of a non-entity (O).

</div>

<div id="S6.SS1.SSS5.p3" class="ltx_para">

Product-version confusion occurs, as in date-based versions like “<span id="S6.SS1.SSS5.p3.1.1" class="ltx_text ltx_font_italic">2017-02-12</span>” in “<span id="S6.SS1.SSS5.p3.1.2" class="ltx_text ltx_font_italic">Android for MSM before 2017-02-12</span>” that cause boundary errors.

</div>

<div id="S6.SS1.SSS5.p4" class="ltx_para">

Heuristic post-processing rules partially mitigate these errors by reclassifying year-based identifiers (e.g., “<span id="S6.SS1.SSS5.p4.1.1" class="ltx_text ltx_font_italic">2007</span>”) as versions and normalizing complex version patterns, improving boundary detection. We also utilized context clues (e.g., prepositions like “<span id="S6.SS1.SSS5.p4.1.2" class="ltx_text ltx_font_italic">for</span>”) to distinguish platforms and by flagging common product name suffixes like “<span id="S6.SS1.SSS5.p4.1.3" class="ltx_text ltx_font_italic">Edition</span>” as I-PN, reducing misclassifications.

</div>

<div id="S6.SS2" class="section ltx_subsection">

### <span class="ltx_tag ltx_tag_subsection"><span id="S6.SS2.4" class="ltx_text">VI-B</span> </span><span id="S6.SS2.5" class="ltx_text ltx_font_italic">Experiment II: Vulnerability Retrieval</span>

<div id="S6.SS2.SSS1" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S6.SS2.SSS1.4" class="ltx_text">VI-B</span>1 </span>Dataset

<div id="S6.SS2.SSS1.p1" class="ltx_para">

To simulate a real-world use-case scenario for our comparative analysis, we randomly selected and stored commonly used software packages within our testing environment. We then generated a system configuration file that comprised three distinct components: a network device segment consisting of 4 components, two virtual machines, one based on Linux OS and one based on Windows, with 46 and 22 components, respectively.

</div>

</div>

<div id="S6.SS2.SSS2" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S6.SS2.SSS2.4" class="ltx_text">VI-B</span>2 </span>Steps

<div id="S6.SS2.SSS2.p1" class="ltx_para">

We queried the system’s configuration against multiple vulnerability databases: <span id="S6.SS2.SSS2.p1.1.1" class="ltx_text ltx_font_italic">NVD</span>, <span id="S6.SS2.SSS2.p1.1.2" class="ltx_text ltx_font_italic">cve-search</span>, <span id="S6.SS2.SSS2.p1.1.3" class="ltx_text ltx_font_italic">OpenCVE</span> and our proprietary database. This yields separate sets of vulnerabilities, denoted as $V_{n\hspace{0pt}v\hspace{0pt}d}$, $V_{c\hspace{0pt}v\hspace{0pt}e\hspace{0pt}s\hspace{0pt}e\hspace{0pt}a\hspace{0pt}r\hspace{0pt}c\hspace{0pt}h}$, $V_{o\hspace{0pt}p\hspace{0pt}e\hspace{0pt}n\hspace{0pt}c\hspace{0pt}v\hspace{0pt}e}$ and $V_{o\hspace{0pt}u\hspace{0pt}r}$, respectively. A union set, $V_{u\hspace{0pt}n\hspace{0pt}i\hspace{0pt}o\hspace{0pt}n}$, is constructed from the individual sets to encompass all unique vulnerabilities identified across the databases. We did not involve <span id="S6.SS2.SSS2.p1.1.4" class="ltx_text ltx_font_italic">OSV</span>, <span id="S6.SS2.SSS2.p1.1.5" class="ltx_text ltx_font_italic">Security Database</span> and <span id="S6.SS2.SSS2.p1.1.6" class="ltx_text ltx_font_italic">CVEdetails</span>, due to different focus for <span id="S6.SS2.SSS2.p1.1.7" class="ltx_text ltx_font_italic">OSV</span> and limited accessibility for <span id="S6.SS2.SSS2.p1.1.8" class="ltx_text ltx_font_italic">Security Database</span> and <span id="S6.SS2.SSS2.p1.1.9" class="ltx_text ltx_font_italic">CVEdetails</span>. We further produced several sub-databases considering various query methods provided by <span id="S6.SS2.SSS2.p1.1.10" class="ltx_text ltx_font_italic">NVD API</span>, <span id="S6.SS2.SSS2.p1.1.11" class="ltx_text ltx_font_italic">cve-search</span> and <span id="S6.SS2.SSS2.p1.1.12" class="ltx_text ltx_font_italic">OpenCVE</span> in terms of keyword (exact) match and <span id="S6.SS2.SSS2.p1.1.13" class="ltx_text ltx_font_italic">CPE</span> match, following their official query instructions. For the latter, we use the <span id="S6.SS2.SSS2.p1.1.14" class="ltx_text ltx_font_italic">uCPE</span> metadata generated in our vulnerability pipeline as query tags.

</div>

<div id="S6.SS2.SSS2.p2" class="ltx_para">

A manual verification process is conducted on $V_{\text{union}}$ to determine the applicability of each vulnerability to our system, involving a detailed review of vulnerability reports and matching identified vulnerabilities against the system configuration. Through the manual verification process, we establish a ground-truth dataset $V_{\text{gt}}$, representing the accurately identified vulnerabilities applicable to our system. We then compare $V_{\text{gt}}$ against each database-specific vulnerability set (e.g., $V_{\text{nvd}}$, $V_{\text{cvesearch}}$, $V_{\text{opencve}}$, $V_{\text{our}}$).

</div>

</div>

<div id="S6.SS2.SSS3" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S6.SS2.SSS3.4" class="ltx_text">VI-B</span>3 </span>Evaluation Metrics

<div id="S6.SS2.SSS3.p1" class="ltx_para">

Validation of vulnerability retrieval performance involves calculating FP (or False Positives), FN (or False Negatives), TP (or True Positives), Retrieval Precision and Retrieval Coverage for each dataset. We then calculate the average of them. Here $V_{n}$ denotes a database-specific vulnerability set and $V_{\text{gt}}$ denotes a ground-truth dataset.

</div>

<div id="S6.SS2.SSS3.p2" class="ltx_para">

- <span id="S6.I2.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S6.I2.i1.p1" class="ltx_para">

  FP: Vulnerabilities in $V_{n}$ but not in $V_{g\hspace{0pt}t}$.

  </div>
- <span id="S6.I2.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S6.I2.i2.p1" class="ltx_para">

  FN: Vulnerabilities in $V_{g\hspace{0pt}t}$ but not in $V_{n}$.

  </div>
- <span id="S6.I2.i3"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S6.I2.i3.p1" class="ltx_para">

  TP: Vulnerabilities in both $V_{n}$ and $V_{g\hspace{0pt}t}$.

  </div>
- <span id="S6.I2.i4"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S6.I2.i4.p1" class="ltx_para">

  Retrieval Precision: $\text{TP}/\text{(TP + FP)}$, the fraction of correctly identified vulnerabilities.

  </div>
- <span id="S6.I2.i5"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S6.I2.i5.p1" class="ltx_para">

  Retrieval Coverage: $\text{TP}/\text{(TP + FN)}$, the fraction of actual vulnerabilities correctly identified.

  </div>

</div>

</div>

<div id="S6.SS2.SSS4" class="section ltx_subsubsection">

#### <span class="ltx_tag ltx_tag_subsubsection"><span id="S6.SS2.SSS4.4" class="ltx_text">VI-B</span>4 </span>Results

<div id="S6.SS2.SSS4.p1" class="ltx_para">

The results are summarized in Table <a href="#S6.T7" class="ltx_ref" title="TABLE VII ‣ VI-A5 Error Analysis ‣ VI-A Experiment I: NER/RE Evaluation ‣ VI Experimental Evaluation ‣ VulCPE: Context-Aware Cybersecurity Vulnerability Retrieval and Management"><span class="ltx_text ltx_ref_tag">VII</span></a>. ## <span class="ltx_tag ltx_tag_section">VII </span><span id="S7.1" class="ltx_text ltx_font_smallcaps">Conclusion</span>

<div id="S7.p1" class="ltx_para">

This paper presents VulCPE, a cybersecurity-focused framework that addresses critical challenges in vulnerability management, including data inconsistencies and false positives in existing vulnerability databases. By leveraging NER and RE techniques, VulCPE standardizes vendor, product, and version relationships into a uCPE schema. This approach enhances vulnerability retrieval by resolving inconsistencies, improving context-aware mapping, and enabling accurate applicability assessments across diverse and complex configurations.

</div>

<div id="S7.p2" class="ltx_para">

Experimental studies demonstrated the efficacy of our proposed framework, showcasing better performance in terms of vulnerability retrieval precision and coverage compared to open-source baseline solutions (<span id="S7.p2.1.1" class="ltx_text ltx_font_italic">NVD</span>, <span id="S7.p2.1.2" class="ltx_text ltx_font_italic">cve-search</span>, and <span id="S7.p2.1.3" class="ltx_text ltx_font_italic">OpenCVE</span>). Our proposed query generation mechanism expands vulnerability coverage across all baseline solutions. Moreover, our vulnerability pipeline achieves the highest precision (0.766) and coverage (0.926) in vulnerability retrieval, surpassing figures obtained using <span id="S7.p2.1.4" class="ltx_text ltx_font_italic">NVD</span>, <span id="S7.p2.1.5" class="ltx_text ltx_font_italic">cve-search</span>, and <span id="S7.p2.1.6" class="ltx_text ltx_font_italic">OpenCVE</span>. These outcomes show the efficacy of our automated FP filtering mechanisms. Additionally, VulCPE’s NER and RE models outperform baseline approaches, with the NER model achieving 0.958 precision and 0.975 recall, and the RE model providing more accurate vulnerability-to-version mappings with precision of 0.977 and recall of 0.914.

</div>

<div id="S7.p3" class="ltx_para">

Future work will focus on scaling VulCPE to enterprise environments of varying sizes and industries, exploring integrations with commercial vulnerability management systems, and testing whether more advanced LLMs (e.g., LLama and GPT-x) could be used as alternatives for NER and RE tasks.

</div>
